Enterprise teams need evidence before moving agent work to a different model mix.
A cheaper model may fail important tasks; a routing judge adds overhead and can
make mistakes. This guide uses [NVIDIA NeMo Relay](https://github.com/NVIDIA/NeMo-Relay)
with [NeMo Switchyard](https://nvidia-nemo.github.io/Switchyard/) running as a first
party native plugin to compare a routing policy against fixed-model baselines
using the same tasks and acceptance checks.

The optional [NVIDIA Brev](https://brev.nvidia.com/) example uses the
[pi coding agent](https://github.com/earendil-works/pi/tree/main/packages/coding-agent),
two NVIDIA model targets, and a judge. Switchyard runs inside the Relay process
handling model calls.
The outcome is a scorecard for your policy decision; monetary savings require
validated prices as well as measured usage.

## Before you start

| Requirement | Your deployment | Brev example |
| --- | --- | --- |
| Capture path | Relay handles requests supported by Switchyard's routing contract | pi extension and an OpenAI Chat Completions provider |
| Host | Supported native-plugin platform | Linux x86_64 glibc CPU VM, Python 3.12, Node.js 24.13.1+ |
| Access | Two tool-capable model targets and a JSON-capable judge | NVIDIA API key with access to the selected models |
| Versions | Compatible Relay and Switchyard releases | Relay 0.10.4, pi 0.84.0, Switchyard plugin 0.3.2 |
| Changes and cleanup | Plugin and route policy in the model-handling process | Isolated output, pi configuration, and plugin bundle; remove only those directories |

<Warning title="Keep system policy separate">
Use a host without the coding-agent example's system-wide Relay policy.
An explicit plugin path still merges system configuration.
</Warning>

## 1. Define the decision and acceptance bar

Choose tasks that represent your workload, including cases that may need a
capable model. Hold inputs, tools, output limits, model versions, and acceptance
checks constant. Retain failed attempts and include retries and judge overhead.

| Policy | Purpose |
| --- | --- |
| Fixed capable | Establish the baseline acceptance and resource use. |
| Fixed efficient | Check whether the efficient model alone meets the requirement. |
| Routed | Evaluate whether the selected model mix preserves acceptance with useful resource changes. |

## 2. Install and configure the route

Install a compatible Switchyard bundle, enable its dynamic-plugin declaration,
and load it in the Relay process that receives the model request.

<Warning title="Native-plugin trust">
The plugin executes native code inside Relay. The example's
`attestation = "integrity_only"` accepts a digest-verified unsigned bundle.
A checksum fetched beside an artifact establishes integrity, not independent
publisher authenticity. Use `signature_required` with a signed bundle and your
approved trust configuration for a stricter deployment.
</Warning>

Relay's `plugins.toml` points at the plugin manifest and route file:

```toml
version = 1

[[plugins.dynamic]]
manifest = "/opt/nemo-relay/plugins/switchyard/relay-plugin.toml"

[plugins.dynamic.config]
priority = 0
switchyard_config_path = "/etc/switchyard/routes.toml"

[plugins.policy.overrides."nvidia.switchyard"]
attestation = "integrity_only"
```

Registering a declaration does not enable it. Enable `nvidia.switchyard`, validate
the installed plugin, and restart the affected process. The companion performs
those steps in its isolated configuration.

The following `routes.toml` shows the routing decision explicitly.
Replace the illustrative endpoint and model IDs with accessible targets:

```toml
schema_version = 1

[llm_clients.provider]
format = "openai_chat"
base_url = "https://integrate.api.nvidia.com/v1"
api_key_env = "NVIDIA_API_KEY"

[targets.efficient]
id = "YOUR_EFFICIENT_MODEL"
llm_client = "provider"

[targets.capable]
id = "YOUR_CAPABLE_MODEL"
llm_client = "provider"

[targets.judge]
id = "YOUR_JUDGE_MODEL"
llm_client = "provider"

[routes.baseline]
id = "switchyard/baseline"
type = "passthrough"
target = "capable"

[routes.efficient]
id = "switchyard/efficient"
type = "passthrough"
target = "efficient"

[routes.routed]
id = "switchyard/routed"
type = "llm_classifier"
mode = "capability"
classifier_target = "judge"
strong_target = "capable"
weak_target = "efficient"
base_threshold = 0.8
response_format_type = "json_object"
max_output_tokens = 8192
classify_trigger = "new_session"
message_hash_fallback = true
```

The caller selects the virtual route `switchyard/routed`, rather than a real
target model. The plugin reads the provider key from Relay's environment.
Holding the selection for a session avoids changing targets at every tool
continuation. Each independent task must have a distinct session identity.
See [classifier routing](https://nvidia-nemo.github.io/Switchyard/routing_algorithms/llm_classifier_routing/)
for judge requirements, thresholds, and session-affinity options.


[plugin release 0.3.2](https://github.com/NVIDIA/NeMo-Relay-Plugins/releases/tag/switchyard-plugin-0.3.2),

[Relay plugin installer](/configure-plugins/plugin-configuration-files).
</Accordion>

## 3. Run comparable work through all policies

Use independent task acceptance checks. A successful model call or agent exit
does not establish that the requested code works. Check the selected model,
served model, classifier recovery, and truncated calls alongside task results.

<Accordion title="Brev example: run the comparison">
Check the [shared runtime setup](/user-guides/about#example-runtimes), then
choose models that your key can access:

```bash
export NVIDIA_BASE_URL=https://integrate.api.nvidia.com/v1
export EFFICIENT_MODEL=YOUR_EFFICIENT_MODEL
export CAPABLE_MODEL=YOUR_CAPABLE_MODEL
export JUDGE_MODEL=YOUR_JSON_CAPABLE_JUDGE
IFS= read -r -s -p 'NVIDIA API key: ' NVIDIA_API_KEY; printf '\n'
export NVIDIA_API_KEY
python3.12 run.py --output /tmp/relay-routing --repeat 3
python3.12 summarize.py /tmp/relay-routing
```

The runner uses fresh scaffolds for incident-ID validation, retry delays, and
dependency planning. The latter includes cycles, transitive blocking, lexical
topological order, and a 10,000-node chain. It tests a broader capability boundary;
observe the judge's actual selection rather than assuming it chooses the capable model.

Three tasks, three policies, and three repetitions produce 27 attempts, with
policy order rotated between trials. Use `--repeat 1` for an initial check.
External acceptance runs outside the agent's working directory. Every arm has
the same tools and 16,384-token answer budget. Failures remain in `results.json`;
the overall command returns nonzero if any arm fails.

Choose available models from [build.nvidia.com](https://build.nvidia.com/explore/discover).
The API base URL is `https://integrate.api.nvidia.com/v1`; requests use
`/chat/completions`. Confirm that your key can access each target before starting.
</Accordion>

## 4. Interpret task quality and routing together

Compare the routed policy with both fixed-model baselines on your workload.
Read resource changes alongside task acceptance, including failed attempts.

| Signal | How to interpret it |
| --- | --- |
| Task acceptance | Similar totals can hide failures on different tasks. Inspect which requirements each policy missed. |
| Elapsed time | Compare repeated task durations and slow cases. Include judge calls, retries, and timeouts. |
| Answer usage | Compare input and output tokens by served model. Lower token totals alone do not establish lower cost. |
| Judge overhead | Include classification usage and latency when evaluating the whole workflow. |
| Routing mix | Check whether selections match task needs. If a policy always chooses the same target, compare it with that fixed-model baseline. |
| Recoveries and truncation | Inspect invalid verdicts, fallback reasons, and incomplete calls before attributing results to the routing policy. |

<Note title="A selected model is not a completed task">
Confirm the served model and acceptance result. A capable selection caused by
an invalid judge verdict does not demonstrate successful classification.
Keep missing usage or pricing marked unknown.
</Note>

<Accordion title="Brev example: locate the evidence">

| Evidence | Inspect |
| --- | --- |
| Task acceptance | `results.json`, generated files, and `acceptance.log` |
| Selection and delivery | `switchyard.routing.decision`: `selected_model`, `served_model`, `fallback_used` |
| Judge recovery | Decision `evidence.source` and `reason_code` |
| Provider attempts | `switchyard.routing.llm_call`: `call_role`, model, and outcome |
| Usage and truncation | `summary.json`, answer/routing metrics, and incomplete model calls |

Judge HTTP success does not establish a valid verdict. Review final JSON and
recovery reasons alongside the task's acceptance log.
</Accordion>

### Add cost when prices are known

Price input and output usage separately for each target, including judge calls
and retries. Missing usage or pricing remains unknown. Token totals alone cannot
establish savings when models and token types have different prices.

```text
Workload cost = answer-model cost + judge cost
Cost per accepted task = workload cost / accepted tasks
```

Compare the result with the fixed-capable baseline using your validated
[pricing catalog](/configure-plugins/model-pricing). Apply your task-quality
requirement before accepting a cost improvement.

## 5. Refine and validate the policy

If routing misses required tasks, inspect the chosen target, judge verdict, and
failure evidence. If acceptance holds but resource use grows, check judge
frequency, retries, and model usage. When the efficient baseline already meets
your requirements, consider whether routing adds useful value.

Change one setting at a time and repeat the comparison. Promote a policy when
task acceptance and the resource improvement hold across representative work
and repeated trials. Re-evaluate after changes to models, providers, or the harness.

## Cleanup and next steps

The runner stops each task gateway. Retain the scorecard and logs, then remove
only your chosen output and plugin-bundle directories. Leave other users' pi
settings and plugin installations in place.
