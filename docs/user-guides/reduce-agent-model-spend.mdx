Use Switchyard when an agent workload already crosses a Relay-managed model
boundary and you want to evaluate a more efficient model mix. Its native Relay
plugin selects an answer model for requests addressed to a configured route ID.
Relay owns the caller-facing boundary and exports the resulting telemetry.
First establish that routing works and task quality holds; add monetary pricing
when you have a credible basis for it.

## What you'll compare

Run two synthetic coding tasks through three model policies: always capable,
always efficient, and Switchyard's classifier. Review accepted tasks, elapsed
time, selected/served models, judge failures, and available token usage together.
The example uses pi and remote NVIDIA inference on an ordinary CPU VM.

```text
pi → Relay gateway + Switchyard plugin → fixed target (baseline arms)
                                    └→ judge → efficient or capable (routed arm)
                     └→ local ATOF events → results.json + summary.json
```

## Prerequisites

- Python 3.12, Node.js 24.13.1+, Git, and the
  [pi quickstart](/getting-started/quick-start/pi) versions: pi **0.84.0** and
  Relay CLI **0.11.0-rc.1**. The pi integration remains a proof of concept.
- The public
  [Switchyard plugin 0.3.2 release](https://github.com/NVIDIA/NeMo-Relay-Plugins/releases/tag/switchyard-plugin-0.3.2).
  The Ubuntu x86_64 example downloads it without GitHub authentication.
  Published Linux x86/Arm and macOS Arm bundles are available. Install only a
  trusted native library; it executes inside Relay's process.
- An [NVIDIA API key](https://build.nvidia.com/settings/api-keys) and access to
  tool-capable answer models and a judge supporting JSON-object responses.

## Run the optional comparison

The [companion directory](https://github.com/NVIDIA/NeMo-Relay/tree/topic/codex/user-guides-model-cost/docs/user-guides/_examples/model-routing)
is the review copy until the guide lands upstream. On your Linux CPU host or
Brev instance (`brev shell YOUR_INSTANCE`), clone the branch and install the
bundle into an unused directory:

```bash
git clone --branch topic/codex/user-guides-model-cost --single-branch https://github.com/NVIDIA/NeMo-Relay.git relay-routing
cd relay-routing/docs/user-guides/_examples/model-routing
SWITCHYARD_MANIFEST=$(bash install-plugin.sh /tmp/relay-switchyard-bundle)
export SWITCHYARD_MANIFEST
```

The helper selects the pinned Linux x86_64 glibc asset and checks its SHA-256
sidecar before extraction. For another supported platform, use the
[Relay plugin installer](/configure-plugins/plugin-configuration-files) with
`github:NVIDIA/NeMo-Relay-Plugins@switchyard-plugin-0.3.2` and an authenticated
GitHub CLI, then set `SWITCHYARD_MANIFEST` to its installed manifest.

Select your models and supply the API key through your approved secret store.
For an interactive Bash session:

```bash
export NVIDIA_BASE_URL=https://integrate.api.nvidia.com/v1
export EFFICIENT_MODEL=nvidia/nemotron-3-nano-omni-30b-a3b-reasoning
export CAPABLE_MODEL=nvidia/nemotron-3-super-120b-a12b
IFS= read -r -s -p 'NVIDIA API key: ' NVIDIA_API_KEY; printf '\n'
export NVIDIA_API_KEY
python3.12 run.py --output /tmp/relay-routing-comparison --repeat 3
python3.12 summarize.py /tmp/relay-routing-comparison
```

The model IDs above are published candidates
([Nano Omni](https://build.nvidia.com/nvidia/nemotron-3-nano-omni-30b-a3b-reasoning),
[Super](https://build.nvidia.com/nvidia/nemotron-3-super-120b-a12b)), **not a
live-validated pairing for this workload**. Substitute accessible models after
checking tool support, context limits, and judge verdicts. `JUDGE_MODEL` defaults
to the efficient model. Single trials are noisy; `--repeat 3` runs 18 tasks and
rotates arm order between trials. API usage depends on the chosen models and
number of calls. No GPU or monetary-cost claim is required for this comparison.

## Establish a comparable baseline

Choose tasks with a concrete acceptance criterion, including work that may need
the capable model. Keep inputs, tools, context/output limits, model versions,
and acceptance checks constant across the runs. Include failed tasks and retries
in your record. A larger model is not automatically better on your workload.

The companion uses two small code changes in a service: normalize incident IDs
and implement a capped retry policy. Each arm receives a fresh source scaffold;
acceptance checks run outside the agent's working directory. Each arm has the
same `read`, `write`, and `bash` tools and a configurable 16384-token per-call
output budget. Reasoning models can exhaust a smaller limit before editing code;
review `truncated_calls` in the scorecard, even when pi exits zero. Use a larger,
representative task set before changing a production policy.

| Comparison arm | Switchyard behavior | What it establishes |
| --- | --- | --- |
| Fixed capable model | Passthrough route to the capable target | The baseline quality and resource usage. |
| Fixed efficient model | Passthrough route to the efficient target | Whether routing has anything to improve over the efficient model alone. |
| Routed models | Capability classifier chooses between the targets | Whether the model mix retains accepted results with different usage or latency. |

All three arms use Relay and the same plugin. The companion records task status,
acceptance, and elapsed time in `results.json`; its local ATOF files retain the
model/tool activity and routing evidence. Real prices are deliberately omitted
from the first comparison.

## Put the route behind Relay

Install a trusted, compatible Switchyard native-plugin bundle in the Relay
process that handles model calls. The plugin is published separately; the
pinned bundle requires Relay `>=0.10.0, <1.0.0`. Public release assets are
available; the CLI selects the matching architecture. Validate the artifact and
its publisher before loading it. Checksums establish integrity, not independent
publisher authenticity.

The following Relay entry points at the installed manifest and deployment file:

```toml
[[plugins.dynamic]]
manifest = "/opt/nemo-relay/plugins/switchyard/relay-plugin.toml"

[plugins.dynamic.config]
priority = 0
switchyard_config_path = "/etc/switchyard/routes.toml"

[plugins.policy.overrides."nvidia.switchyard"]
attestation = "integrity_only"
```

Registration alone leaves a dynamic plugin disabled. After configuring it,
explicitly enable `nvidia.switchyard`, validate it, and restart the affected
Relay process. The companion runner performs those lifecycle steps in its
isolated example configuration. The trust override accepts a digest-verified
unsigned bundle; signed enterprise builds can use a stricter policy. See
[Switchyard plugin setup](https://nvidia-nemo.github.io/Switchyard/integrations/nemo_relay/#set-up-the-plugin)
for bundle acquisition, verification, and activation.

## Verify routing and task quality

<Steps>
<Step title="Confirm the request crosses the route">
Find the requested virtual route ID and the observed model and tool calls in
the same run. Requests must reach Relay's supported model boundary with a
configured route ID; an unmatched name is passed to its next handler. Do not
infer routing from a successful agent answer alone.
</Step>

<Step title="Inspect selected and served targets">
Inspect Switchyard marks for the selected model, model that actually served the
answer, fallback, routing time, and available token usage. A judge failure can
send all calls to the capable model. Check those failures before interpreting
an apparently successful routed run. A task set need not exercise both targets;
record what actually happened.
</Step>

<Step title="Compare accepted tasks and resource usage">
Review the same acceptance checks for all arms. Compare task completion, review
quality, latency, retries, and available answer/routing token usage. Keep missing
usage visible. The first proof of concept establishes behavior; defer savings
claims until pricing and representative workload evidence are available.
</Step>
</Steps>

The native plugin emits routing marks and metrics through Relay observability.
The companion uses local ATOF evidence; add an approved OTLP destination when
your team needs to inspect the comparison centrally. See the
[Switchyard telemetry contract](https://nvidia-nemo.github.io/Switchyard/integrations/nemo_relay/#routing-telemetry)
for mark fields and the distinction between trace and metric views.

## Keep routing decisions stable during a task

The companion classifies the opening task once, then reuses the selected model
across tool calls. `classify_trigger = "new_session"` and
`message_hash_fallback = true` provide this behavior. Each fixture task starts a
fresh gateway; a persistent enterprise gateway should use explicit session
identity because identical opening messages can share the fallback key.

The judge has an 8192-token budget covering reasoning and final JSON. Inspect
invalid verdicts and truncation before interpreting its choices. The fixture
retains default model reasoning: the pinned plugin requires identical client
and inference settings when judge and answer roles share a model ID.

Before inference, the runner starts the gateway with `pi --version`. This
checks route activation beyond manifest validation. On failure, inspect
`startup.log`. Task timeouts stop detached pi descendants as well as Relay;
process enumeration requires `ps` (procps on Ubuntu).

## Read the scorecard

`results.json` retains each task's arm, trial, exit status, acceptance result,
and elapsed seconds. `summary.json` adds selected answer-call attempts, actual
served model counts, judge errors, classifier recoveries, answer fallback flags, truncated calls, and answer/routing token totals.
The terminal table includes these fields; `summary.json` also records `truncated_calls`:

| Arm | Tasks accepted | Seconds | Efficient attempts | Capable attempts | Judge errors / classifier recovery / answer fallback | Answer tokens | Routing tokens |
| --- | --- | --- | --- | --- | --- | --- | --- |
| baseline / efficient / routed | Passed / attempted | Includes failed trials | Selected target calls | Selected target calls | Check unknown flags too | Total or unknown | Total or unknown |

This describes the output schema; it is not measured model performance.
Answer-call attempts can exceed task count. Inspect `served_models` separately:
a selected model and the model that served the response can differ. Missing or
partial usage stays **unknown**. The summarizer uses only `token_type=total`
from `switchyard.routing.llm_tokens` metric marks, so it does not double-count
input/output constituents. See the companion README for coverage limits.

<Accordion title="Routing mark fields to inspect">
Find a mark named `switchyard.routing.decision`. Its `data` includes
`selected_model`, nullable `served_model`, nullable `fallback_used`, and
`algorithm`. A `switchyard.routing.llm_call` mark identifies
`call_role` (`routing` or `answer`), `selected_model`, and `outcome` (`ok` or
`error`). Metric measurements use `call_role`, `target_model`, and `token_type`.
An invalid judge verdict can recover to the capable model even with an `ok`
HTTP call and `fallback_used=false`. Check `evidence.source` (`fail_open` or
`fall_open` in 0.3.2) and `reason_code`; the summary records classifier recoveries
separately. These are the pinned plugin's fields, not a captured example trace.
</Accordion>

<Note title="Limits of the example">
The tasks and targets are example choices. Use a larger representative task set
before changing production routing. The runner isolates pi and Relay user
configuration, while administrator policy still applies. It is not a filesystem
sandbox. Run trusted tasks on a disposable VM. Timeouts stop the task process
group and preserve partial files; missing routing decisions fail the run's
telemetry check. Successful acceptance alone does not establish routing quality.
</Note>

## A successful pilot on Brev

The revised companion completed all six tasks in about nine minutes, including
startup, on the same organization-accessible NVIDIA endpoint and model pair
shown below. Every arm used the same explicit ASCII contract, stronger external
checks, model defaults, and 16384-token answer budget:

| Arm | Accepted | Seconds | Answer tokens | Judge tokens |
| --- | --- | --- | --- | --- |
| baseline | 2/2 | 354.0 | 48,434 | No judge calls |
| efficient | 2/2 | 100.3 | 117,270 | No judge calls |
| routed | 2/2 | 100.9 | 95,441 | 5,460 |

Each arm made 16 successful answer calls. Baseline used Super; efficient and
routed used Nano. The routed arm made **two successful judge calls**, then
retained its decisions across 14 tool continuations. It recorded no judge
errors, classifier recoveries, answer fallbacks, or truncated calls. The runner
returned zero after task and routing checks passed.

These two tasks did not require a mixed routed model selection. They establish
this fixture's quality and routing behavior, not a production quality guarantee
or monetary savings. Nano used more answer tokens than Super; add validated
prices before interpreting spend. The pilot used `--repeat 1` and a 240-second
task timeout. Repeat with the documented default timeout and rotated arm order
before drawing conclusions about latency or repeatability.

These results do not establish savings or an acceptable production quality bar.
Choose or tune a policy that meets your task requirements, then repeat on a
larger workload before deployment. Failed trials remain part of the comparison.
</Warning>

## Add monetary comparison when ready

When you have validated prices, combine Relay's answer cost with Switchyard
usage classified as `call_role = "routing"`, priced by its `target_model`.
Do not add the `answer` metrics again or sum the `total` token rollup with its
constituents. Missing usage or missing prices remain unknown, rather than zero.

```text
Observed workload cost = Relay answer cost + routing-token cost
Cost per accepted task = observed workload cost / accepted tasks
```

Exported routing metrics do not carry Relay request identity, so reconcile that
cost at the workload or time-window level. The
[model-pricing reference](/configure-plugins/model-pricing) explains how to supply
prices when your provider omits them.

## Cleanup and next steps

After the runner stops, retain the task logs and scorecard you need, then remove
only your chosen comparison output and dedicated bundle directory. The runner
uses isolated plugin state, so no global plugin needs disabling. Leave other
users' plugin installations and pi settings in place.

Adapt the [route schema](https://nvidia-nemo.github.io/Switchyard/reference/toml_schema/)
to your workload, or send comparison telemetry to your approved backend with
[Observability configuration](/configure-plugins/observability/configuration).
Add monetary pricing only when model/usage coverage and prices are verified.
