Enterprise platform teams need a consistent way to route supported coding-agent
activity, apply telemetry policy, and audit what happened while developers keep
their usual tools. The [NVIDIA NeMo Relay](https://github.com/NVIDIA/NeMo-Relay)
daemon brokers those connections and coordinates
workers running under each user's operating-system identity.

This guide covers managed routing, supported model/tool capture, and telemetry
redaction. Identity-provider enrollment, offboarding, and preventing alternate
network routes require your organization's additional controls.

The optional [NVIDIA Brev](https://brev.nvidia.com/) example runs either
[Anthropic Claude Code](https://claude.com/product/claude-code) or
[OpenAI Codex](https://github.com/openai/codex) under two Linux users.

<Tip title="Try the complete example on Brev">
[Run the Brev example](#run-the-brev-example) to provision a shared daemon and
observe two independent Linux users running the same coding harness. The example
installs its policy and routing tokens; no separate daemon setup is needed first.
</Tip>

## Before you start

| Requirement | Your deployment | Brev example |
| --- | --- | --- |
| Host | Supported workstations and a local or remote daemon | Fresh Ubuntu systemd CPU VM with sudo, Git, curl, Python 3.12 |
| Harness | A supported harness and approved provider authentication | Choose Claude Code for both users, or Codex for both |
| Access | Administrator-managed policy and trace intake | Each Linux user signs into the chosen provider separately |
| Changes | Managed bundle, service, worker policy, and user credentials | Creates three accounts, a system service, and files under /etc and /opt |
| Cleanup | Follow your workstation removal runbook | [Remove the deployment](/daemon/operations#remove-a-deployment) or delete the disposable VM |

<Warning title="Dedicated host">
The example installs system-wide Relay policy. Use a separate VM from the
observability and routing examples; a virtual environment does not isolate this policy.
</Warning>

Example versions: Relay 0.10.4, Python 3.12, and either Claude Code 2.1.309 or
Codex 0.164.0. The [support matrix](/reference/support-matrix) lists minimums;
repeat acceptance after changing a version.

## 1. Choose coverage and topology

Inventory the harness version, provider API, required hooks, and operating system.
Model calls must pass through a worker to receive model policy or telemetry.
Supported hooks contribute tool and turn activity; coverage differs by harness.

</Card>
<Card title="Remote daemon" href="/daemon/remote-server" icon="fa-solid fa-server">

For required audit coverage, use `--require-worker` on the daemon:

```ini
ExecStart=/opt/nvidia/bin/nemo-relay daemon --bind 127.0.0.1 --port 47632 --require-worker
```

Without it, allowed pass-through can return a provider response while no worker
is capturing the request. Verify the worker and plugin output before accepting
a cohort. Consult the [support matrix](/reference/support-matrix) for capture limits.

## 2. Apply the managed policy

Distribute an administrator-owned bundle and worker `plugins.toml`. Keep provider
credentials in each user's authentication store; do not place them in shared
configuration. This policy redacts selected emitted fields and exports metadata
to Phoenix, with full payload capture disabled:

```toml
version = 1

[[components]]
kind = "pii_redaction"
enabled = true

[components.config]
version = 1

[[components.config.profiles]]
mode = "builtin"
priority = 80

[components.config.profiles.builtin]
action = "redact"
detector = "email"

[[components.config.profiles]]
mode = "builtin"
priority = 90

[components.config.profiles.builtin]
action = "redact"
detector = "api_key"

[[components]]
kind = "observability"
enabled = true

[components.config]
version = 4
enable_full_payloads = false

[components.config.opentelemetry]
enabled = true

[[components.config.opentelemetry.endpoints]]
type = "openinference"
endpoint = "http://127.0.0.1:6006/v1/traces"
transport = "http_binary"
service_name = "relay-managed-coding-agents"
```

Lower profile priorities run first: email at 80, then API keys at 90. These two
detectors are a sample policy, not comprehensive PII coverage. Other built-in
detectors include phone, IPv4/IPv6, URL, UUID, bearer token, JWT, credit card,
and AWS, GCP, and Azure credential patterns. Select and test detectors for your data using the
[detector reference](/configure-plugins/pii-redaction/configuration#detector-presets).

Redaction affects emitted telemetry, not the conversation sent to the provider.
For another destination, replace the endpoint and authentication using
[Connecting to Observability Platforms](/user-guides/connecting-to-observability-platforms).

## 3. Provision users and managed sessions

Each user-machine identity needs its own routing token. As that user:

```bash
nemo-relay daemon token ensure --json
```

Relay generates 32 random bytes, stores the token in the resolved user configuration
directory, and reports its path without printing its value. On Unix the file
has mode 0600 and its newly created directory has mode 0700. Hooks, MCP registration,
and provider routing must use the same token.

<Note title="Trust boundaries on a shared host">
A different user cannot read an owner-only token file under normal account
permissions; root and processes running as its owner can. This token selects a managed identity;
it does not replace provider authentication or enterprise SSO.

Other local users can query the loopback worker-status endpoint. It exposes
operational state without a username mapping. Keep this endpoint within your trusted operational network. Removing a token file does not revoke its existing
daemon binding: restart the daemon to clear bindings, then provision and
reconnect approved clients. See [credential lifecycle](/daemon/configuration#replace-a-client-token).
</Note>

## 4. Verify attribution, activity, and privacy

Accept one user first, then repeat with multiple concurrent sessions:

| Check | Pass condition |
| --- | --- |
| Worker isolation | Ready workers run under their users' OS accounts. |
| Task completion | Each repository contains the implementation and tests; the task contract and independent checks pass. |
| Captured work | Supported model and tool spans are present and connected to the expected task or turn. |
| Attribution | Record which worker/session and run time belong to each OS account; confirm the corresponding trace. |
| Privacy | Restricted fields are absent or redacted according to the approved telemetry policy. |
| Independent lifetime | A user's worker stops after its final session ends; other users' captured work continues. |

The trace's `nemo_relay.uuid` and `nemo_relay.parent_uuid` establish scope identity
and parentage; `nemo_relay.session.instance_id` identifies the emitted session
where supplied. These are not employee usernames. Join session evidence with
worker lifecycle logs, process ownership, and your enrollment inventory.
Do not infer a person from the shared `service_name` alone.

## <Icon icon="rocket" size={6} /> Run the Brev example

Complete this section in order on a fresh host. It installs the shared service,
managed policy, and user credentials described above. Supporting deployment
references are optional.

### 1. Provision and connect to a VM

In the [Brev Console](https://brev.nvidia.com/), create a fresh instance using
these recommended starting resources. See [Brev provisioning](https://docs.nvidia.com/brev/cli/instance-creation)
for instance selection; available CPU types depend on your organization and provider.

| Setting | Recommendation |
| --- | --- |
| Operating system | Ubuntu 24.04 LTS, x86_64 |
| CPU and memory | 4 vCPUs and 16 GB RAM |
| Storage | At least 40 GB |
| GPU | None; inference runs on the model provider |
| Access | Administrator account with sudo and outbound HTTPS |

These are starting resources for the example, not Relay sizing requirements.
Use a separate VM from the other examples, because system-wide plugin policy
can affect other Relay processes on the same host.

On your **local computer**, install the Brev CLI if needed. On macOS:

```bash
brew install brevdev/homebrew-brev/brev
```

For other operating systems, use the [Brev CLI installation instructions](https://docs.nvidia.com/brev/getting-started/quickstart).
Connect to the instance you created:

```bash
brev login
brev refresh
brev list
brev shell YOUR_INSTANCE
```

Run the remaining setup in **Bash on the VM host**. For the coding-agent example,
PID 1 must be systemd; a workspace container does not satisfy that requirement.

### 2. Install the runtimes and choose one harness

```bash
sudo apt-get update
sudo apt-get install -y ca-certificates curl git python3.12 python3.12-venv xz-utils
curl -LsSf https://astral.sh/uv/install.sh | sh
export PATH="$HOME/.local/bin:$PATH"
python3.12 --version
uv --version
git --version
```

Install Node.js 24.13.1 system-wide so login shells can find the same runtime:

```bash
curl -fsS https://nodejs.org/dist/v24.13.1/node-v24.13.1-linux-x64.tar.xz -o /tmp/node-v24.13.1-linux-x64.tar.xz
curl -fsS https://nodejs.org/dist/v24.13.1/SHASUMS256.txt -o /tmp/node-24.13.1-SHASUMS256.txt
(cd /tmp && awk '$2 == "node-v24.13.1-linux-x64.tar.xz"' node-24.13.1-SHASUMS256.txt | sha256sum --check)
sudo tar -xJf /tmp/node-v24.13.1-linux-x64.tar.xz -C /usr/local --strip-components=1
node --version
npm --version
```

Choose **one** harness to install for both users. Each user will authenticate
separately after provisioning; a laptop login does not sign in a Linux account.

<Tab title="Both users: Claude Code">

```bash
sudo npm install --global --prefix /usr/local @anthropic-ai/claude-code@2.1.309
claude --version
```

</Tab>
<Tab title="Both users: Codex">

sudo npm install --global --prefix /usr/local @openai/codex@0.164.0

A deployment can support multiple harnesses. This example selects one to keep
the two-user setup consistent. Provider subscriptions or API access must permit

Confirm the host before installing the daemon:

```bash
uname -m
ps -p 1 -o comm=
sudo -v
python3.12 -c 'import sys, tomllib; assert sys.version_info >= (3, 12); print("Python ready")'
for account in alice bob nemo-relay; do
  if id "$account" >/dev/null 2>&1; then
    echo "Existing account: $account. Use a fresh VM."
  fi
done
```

Expect `x86_64`, `systemd`, successful sudo/Python checks, and no existing-account
messages. The provisioning script also refuses existing deployment files.

### 3. Provision the managed deployment

Install Relay and provision the selected harness:

```bash
curl -fsSL https://raw.githubusercontent.com/NVIDIA/NeMo-Relay/0.10.4/install.sh -o /tmp/install-relay.sh
NEMO_RELAY_VERSION=0.10.4 sh /tmp/install-relay.sh
export PATH="$HOME/.local/bin:$PATH"
git clone --depth 1 https://github.com/NVIDIA/NeMo-Relay.git relay-coding-agents
cd relay-coding-agents/docs/user-guides/_examples/coding-agents
# Choose claude OR codex. Both accounts use this selection.
sudo bash deploy.sh "$(command -v nemo-relay)" claude "$(command -v python3.12)"
```

Use `codex` in the deployment command if you installed Codex. The provisioning script:

- Creates Alice, Bob, and the dedicated service account, with private home directories.
- Installs Relay and the selected read-only managed bundle under `/opt/nvidia`.
- Creates distinct per-user tokens and task repositories.
- Installs policy under `/etc/nemo-relay` and a systemd service on loopback port 47632.
- Prepares managed Codex settings and a local plugin marketplace when Codex is selected.

<Note title="Provisioning handles the manual deployment steps">
Do not copy the policy or run `nemo-relay daemon token ensure --json` from the
earlier guide steps. `deploy.sh` installs the example policy and creates a private
routing token for each user. Provider login and harness plugin registration still
happen inside each user's account below.
</Note>

Check the service with `sudo systemctl is-active nemo-relay.service`; expect `active`.

Start Phoenix in another terminal with `uvx --from arize-phoenix phoenix serve`.
For the synthetic redaction check only, opt into payloads before starting sessions:

```bash
sudo install -m 0644 plugins.synthetic.toml /etc/nemo-relay/plugins.toml
sudo systemctl restart nemo-relay.service
```

Use only the supplied synthetic task with that policy.

### 4. Authenticate and start both users

Open two local terminals and run `brev shell YOUR_INSTANCE` in each.
From those **administrator shells**, enter the two accounts:

```bash
# First terminal
sudo -iu alice
```

```bash
# Second terminal
sudo -iu bob
```

Use `exit` to return to the administrator shell before switching users. Alice
and Bob have no example password; run sudo from the original administrator account. Inside **each** account, follow the
same chosen harness tab. A laptop login does not sign in a different Linux user.

<Tabs>
<Tab title="Both users: Claude Code">

```bash
claude auth login
claude auth status
/opt/nvidia/share/relay-user-guide/session.sh
```

Use your organization's approved account or API authentication. For a subscription
login, leave provider credential overrides unset and retain the provider's
authorization headers. Check Anthropic's
[subscription and gateway requirements](https://code.claude.com/docs/en/llm-gateway#subscriptions-and-gateways)
for the account and gateway you use.

</Tab>
<Tab title="Both users: Codex">

The deployment script prepares a local plugin catalog. Register it and install
Relay's integration using the documented
[managed Codex installation](/daemon/configuration#codex):

```bash
codex plugin marketplace add /opt/nvidia/share/nemo-relay-codex-marketplace-v1
codex plugin add nemo-relay-managed-v1@nemo-relay-managed
codex login --device-auth
codex login status
/opt/nvidia/share/relay-user-guide/session.sh
```

Device login must be allowed by your workspace. An OpenAI API key is another
authentication option; see [Codex authentication](https://developers.openai.com/codex/auth).

</Tab>
</Tabs>

Review plugin/hook trust prompts and retain required command approvals.
At each harness prompt, enter:

```text
Read /opt/nvidia/share/relay-user-guide/task.txt and complete it in the current repository. Use local files and tests only.
```

Keep Alice's session open while starting Bob.
In another terminal on your **local computer**, forward Phoenix:

```bash
brev port-forward YOUR_INSTANCE --port 6006:6006
```

Open [Phoenix](http://localhost:6006).

### 5. Verify independent activity

Run these commands from an **administrator shell** while both sessions remain open:
```bash
curl -fsS http://127.0.0.1:47632/_nemo_relay/v1/workers/status
ps -eo user,pid,args | grep -E '[n]emo-relay daemon (mcp|worker)'
sudo journalctl -u nemo-relay.service -n 50 --no-pager
sudo -iu alice bash -lc 'cd ticket-service && python3 -m unittest discover'
sudo -iu bob bash -lc 'cd ticket-service && python3 -m unittest discover'
sudo -iu alice bash -lc 'python3 /opt/nvidia/share/relay-user-guide/verify_task.py "$HOME/ticket-service"'
sudo -iu bob bash -lc 'python3 /opt/nvidia/share/relay-user-guide/verify_task.py "$HOME/ticket-service"'
```

Status reports `worker_id`, `state`, `reference_count`, `control_available`, and
`in_flight`; it does not test provider capture. In Phoenix project `default`,
find service `relay-managed-coding-agents` at each task's time. Inspect the
`task.txt` tool result for redaction and the model/tool parentage.

A successful process exit is insufficient: noninteractive harnesses can return
zero while policy prevents the task's commands. Check the files and run the tests.
Validate ASCII prefixes as well as ASCII digits; Unicode lookalikes must be rejected.

Expect two ready workers and successful independent task checks for both users.
Record each account's worker/session and task time, then inspect its model/tool
trace and synthetic redaction in Phoenix. Close Alice's session, wait for its
worker to shut down, and ask Bob to run his tests again. Confirm Bob's worker
remains available and the follow-up produces a new captured turn.

### 6. Clean up

Close both harnesses and retain the evidence. Restore metadata-only capture
before using real data. For this disposable example, stop Phoenix and delete the
VM, or follow [Remove a Deployment](/daemon/operations#remove-a-deployment).
