Enterprise platform teams need a consistent way to route supported coding-agent
activity, apply telemetry policy, and audit what happened while developers keep
their usual tools. The [NVIDIA NeMo Relay](https://github.com/NVIDIA/NeMo-Relay)
daemon brokers those connections and coordinates
workers running under each user's operating-system identity.

This guide covers managed routing, supported model/tool capture, and telemetry
redaction. Identity-provider enrollment, offboarding, and preventing alternate
network routes require your organization's additional controls.

The optional [NVIDIA Brev](https://brev.nvidia.com/) example runs either
[Anthropic Claude Code](https://claude.com/product/claude-code) or
[OpenAI Codex](https://github.com/openai/codex) under two Linux users.

## Before you start

| Requirement | Your deployment | Brev example |
| --- | --- | --- |
| Host | Supported workstations and a local or remote daemon | Fresh Ubuntu systemd CPU VM with sudo, Git, curl, Python 3.12 |
| Harness | A supported harness and approved provider authentication | Choose Claude Code for both users, or Codex for both |
| Access | Administrator-managed policy and trace intake | Each Linux user signs into the chosen provider separately |
| Changes | Managed bundle, service, worker policy, and user credentials | Creates three accounts, a system service, and files under /etc and /opt |
| Cleanup | Follow your workstation removal runbook | [Remove the deployment](/daemon/operations#remove-a-deployment) or delete the disposable VM |

<Warning title="Dedicated host">
The example installs system-wide Relay policy. Use a separate VM from the
observability and routing examples; a virtual environment does not isolate this policy.
</Warning>

Example versions: Relay 0.10.4, Python 3.12, and either Claude Code 2.1.309 or
Codex 0.164.0. The [support matrix](/reference/support-matrix) lists minimums;
repeat acceptance after changing a version.

## 1. Choose coverage and topology

Inventory the harness version, provider API, required hooks, and operating system.
Model calls must pass through a worker to receive model policy or telemetry.
Supported hooks contribute tool and turn activity; coverage differs by harness.

</Card>
<Card title="Remote daemon" href="/daemon/remote-server" icon="fa-solid fa-server">

For required audit coverage, use `--require-worker` on the daemon:

```ini
ExecStart=/opt/nvidia/bin/nemo-relay daemon --bind 127.0.0.1 --port 47632 --require-worker
```

Without it, allowed pass-through can return a provider response while no worker
is capturing the request. Verify the worker and plugin output before accepting
a cohort. Consult the [support matrix](/reference/support-matrix) for capture limits.

## 2. Apply the managed policy

Distribute an administrator-owned bundle and worker `plugins.toml`. Keep provider
credentials in each user's authentication store; do not place them in shared
configuration. This policy redacts selected emitted fields and exports metadata
to Phoenix, with full payload capture disabled:

```toml
version = 1

[[components]]
kind = "pii_redaction"
enabled = true

[components.config]
version = 1

[[components.config.profiles]]
mode = "builtin"
priority = 80

[components.config.profiles.builtin]
action = "redact"
detector = "email"

[[components.config.profiles]]
mode = "builtin"
priority = 90

[components.config.profiles.builtin]
action = "redact"
detector = "api_key"

[[components]]
kind = "observability"
enabled = true

[components.config]
version = 4
enable_full_payloads = false

[components.config.opentelemetry]
enabled = true

[[components.config.opentelemetry.endpoints]]
type = "openinference"
endpoint = "http://127.0.0.1:6006/v1/traces"
transport = "http_binary"
service_name = "relay-managed-coding-agents"
```

Lower profile priorities run first: email at 80, then API keys at 90. These two
detectors are a sample policy, not comprehensive PII coverage. Other built-in
detectors include phone, IPv4/IPv6, URL, UUID, bearer token, JWT, credit card,
and AWS, GCP, and Azure credential patterns. Select and test detectors for your data using the
[detector reference](/configure-plugins/pii-redaction/configuration#detector-presets).

Redaction affects emitted telemetry, not the conversation sent to the provider.
For another destination, replace the endpoint and authentication using
[Connecting to Observability Platforms](/user-guides/connecting-to-observability-platforms).

## 3. Provision users and managed sessions

Each user-machine identity needs its own routing token. As that user:

```bash
nemo-relay daemon token ensure --json
```

Relay generates 32 random bytes, stores the token in the resolved user configuration
directory, and reports its path without printing its value. On Unix the file
has mode 0600 and its newly created directory has mode 0700. Hooks, MCP registration,
and provider routing must use the same token.

<Note title="Trust boundaries on a shared host">
Bob cannot read Alice's owner-only token file under normal account permissions;
root and processes running as Alice can. This token selects a managed identity;
it does not replace provider authentication or enterprise SSO.

Other local users can query the loopback worker-status endpoint. It exposes
operational state without a username mapping. Keep it
on loopback for this example. Removing a token file does not revoke its existing
daemon binding: restart the daemon to clear bindings, then provision and
reconnect approved clients. See [credential lifecycle](/daemon/configuration#replace-a-client-token).
</Note>

<Accordion title="Brev example: provision two users with one harness">
Install Relay from a stable, pinned installer and select one harness for both users:

```bash
curl -fsSL https://raw.githubusercontent.com/NVIDIA/NeMo-Relay/0.10.4/install.sh -o /tmp/install-relay.sh
NEMO_RELAY_VERSION=0.10.4 sh /tmp/install-relay.sh
export PATH="$HOME/.local/bin:$PATH"
git clone --depth 1 https://github.com/NVIDIA/NeMo-Relay.git relay-coding-agents
cd relay-coding-agents/docs/user-guides/_examples/coding-agents
# Choose claude OR codex. Both accounts use this selection.
sudo bash deploy.sh "$(command -v nemo-relay)" claude "$(command -v python3.12)"
```

Use `codex` in the deployment command for the Codex variant. Install that harness
where both new users' login shells can find it. The provisioning script:

- Creates Alice, Bob, and the dedicated service account, with private home directories.
- Installs Relay and the selected read-only managed bundle under `/opt/nvidia`.
- Creates distinct per-user tokens and task repositories.
- Installs policy under `/etc/nemo-relay` and a systemd service on loopback port 47632.
- Prepares managed Codex settings and a local plugin marketplace when Codex is selected.

It refuses to overwrite existing users or deployment files. Check Python 3.12
explicitly: with uv, install it using `uv python install 3.12` and pass the
absolute path from `uv python find 3.12`.

Start Phoenix in another terminal with `uvx --from arize-phoenix phoenix serve`.
For the synthetic redaction check only, opt into payloads before starting sessions:

```bash
sudo install -m 0644 plugins.synthetic.toml /etc/nemo-relay/plugins.toml
sudo systemctl restart nemo-relay.service
```

Use only the supplied synthetic task with that policy.
</Accordion>

## 4. Verify attribution, activity, and privacy

Accept one user first, then repeat with both sessions active:

| Check | Pass condition |
| --- | --- |
| Worker isolation | Two ready worker IDs, with processes owned separately by Alice and Bob. |
| Task completion | Each repository contains the implementation and tests; the task contract and independent checks pass. |
| Captured work | Supported model and tool spans are present and connected to the expected task or turn. |
| Attribution | Record which worker/session and run time belong to each OS account; confirm the corresponding trace. |
| Privacy | With the synthetic policy, exported task content contains `[REDACTED]` instead of the synthetic contact. |
| Independent lifetime | Closing Alice removes her worker after shutdown; Bob can complete another captured request. |

The trace's `nemo_relay.uuid` and `nemo_relay.parent_uuid` establish scope identity
and parentage; `nemo_relay.session.instance_id` identifies the emitted session
where supplied. These are not employee usernames. Join session evidence with
worker lifecycle logs, process ownership, and your enrollment inventory.
Do not infer a person from the shared `service_name` alone.

<Accordion title="Brev example: inspect workers and task results">

```bash
curl -fsS http://127.0.0.1:47632/_nemo_relay/v1/workers/status
ps -eo user,pid,args | grep -E '[n]emo-relay daemon (mcp|worker)'
sudo journalctl -u nemo-relay.service -n 50 --no-pager
sudo -iu alice bash -lc 'cd ticket-service && python3 -m unittest discover'
sudo -iu bob bash -lc 'cd ticket-service && python3 -m unittest discover'
sudo -iu alice bash -lc 'python3 /opt/nvidia/share/relay-user-guide/verify_task.py "$HOME/ticket-service"'
sudo -iu bob bash -lc 'python3 /opt/nvidia/share/relay-user-guide/verify_task.py "$HOME/ticket-service"'
```

Status reports `worker_id`, `state`, `reference_count`, `control_available`, and
`in_flight`; it does not test provider capture. In Phoenix project `default`,
find service `relay-managed-coding-agents` at each task's time. Inspect the
`task.txt` tool result for redaction and the model/tool parentage.

A successful process exit is insufficient: noninteractive harnesses can return
zero while policy prevents the task's commands. Check the files and run the tests.
Validate ASCII prefixes as well as ASCII digits; Unicode lookalikes must be rejected.
</Accordion>

## Cleanup and next steps

Close both sessions, retain required evidence, and follow
[Remove a Deployment](/daemon/operations#remove-a-deployment), or delete the
disposable VM. Stop only the Phoenix process you started.

Restore metadata-only capture before introducing real data. Repeat acceptance
after changing a harness, Relay version, provider route, or policy. Add a
validated [pricing catalog](/configure-plugins/model-pricing) if your audit
pipeline also needs cost attribution.
