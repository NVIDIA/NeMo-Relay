Enterprise teams need to investigate agent activity in the observability platform
they already operate. This guide connects a
[NVIDIA NeMo Relay](https://github.com/NVIDIA/NeMo-Relay) capture path to that platform
and verifies that agent or turn activity, model calls, and tools arrive together.
It applies to managed coding agents, framework integrations, and instrumented applications.

The optional [NVIDIA Brev](https://brev.nvidia.com/) example uses a small Python
application and [Arize Phoenix](https://arize.com/phoenix/).
It reads synthetic incident requests, asks a model to prioritize them, and writes
a handoff. [Nous Research Hermes Agent](https://github.com/NousResearch/hermes-agent)
is another example choice; neither harness is required for your deployment.

## Before you start

| Requirement | Your deployment | Brev example |
| --- | --- | --- |
| Relay | A capture path that sees the required model and tool activity | Relay Python SDK 0.10.4; no separate coding agent |
| Host | A platform supported by your chosen integration | CPU Linux VM, Python 3.12, Git, uv |
| Access | Trace-ingestion permission and any provider credentials | NVIDIA API key and an accessible model; local Phoenix needs no API key |
| Changes | Exporter configuration in the process that owns capture | Virtual environment and new output directory; no system service |
| Cleanup | Retain required audit evidence before removal | Stop Phoenix and remove only the example directories you created |

<Warning title="Keep examples isolated">
Use a host without the coding-agent example's system-wide Relay policy.
That policy also applies to SDK and framework processes, including explicit plugin files.
</Warning>

## 2. Enable the plugin and select a destination

Place the following `plugins.toml` in the configuration loaded by that worker
or application. This minimal example sends OpenInference traces to local Phoenix
and omits full prompt and tool payloads:

```toml
version = 1

[[components]]
kind = "observability"
enabled = true

[components.config]
version = 4
enable_full_payloads = false

[components.config.opentelemetry]
enabled = true

[[components.config.opentelemetry.endpoints]]
type = "openinference"
endpoint = "http://127.0.0.1:6006/v1/traces"
transport = "http_binary"
service_name = "relay-support-triage"

[components.config.opentelemetry.endpoints.resource_attributes]
"openinference.project.name" = "relay-support-triage"
```

Workers load administrator-owned system configuration. Framework integrations
load it when they initialize Relay. For a directly instrumented Python application,
import the observability component and activate the host around application work:

```python
from nemo_relay import plugin
import nemo_relay.observability

async with plugin.activate(plugin.PluginConfig(), "plugins.toml"):
    await run_application()
```

Restart or reopen the affected process after changing its configuration.
Check activation diagnostics before testing delivery.
[Plugin initialization](/configure-plugins/initialize-plugins) explains the lifecycle.

Choose the destination recipe for the endpoint, projection, and authentication
changes. Credentials belong in the exporting process's environment;
`header_env` maps header names to environment-variable names.

## 3. Exercise a representative workload

Run work with a clear expected outcome. Keep the service name, run time, and
local event log so you can find the same activity in the destination.
Approve payload fields and redaction policy before enabling payload capture.

<Accordion title="Brev example: instrumented Python application">
Use a disposable CPU instance with the [shared runtime setup](/user-guides/about#example-runtimes).
The SDK example also runs on macOS using the same virtual-environment commands.
On Brev, connect with `brev shell YOUR_INSTANCE`, then:

```bash
git clone --depth 1 https://github.com/NVIDIA/NeMo-Relay.git relay-observability
cd relay-observability/docs/user-guides/_examples/observability
uv venv --python 3.12 .venv
uv pip install --python .venv/bin/python nemo-relay==0.10.4
```

In a second terminal on the same host, start disposable Phoenix:

```bash
uvx --from arize-phoenix phoenix serve
```

Back in the example directory, select a tool-capable model from the
[NVIDIA API catalog](https://build.nvidia.com/explore/discover) and enter its API key:

```bash
export NVIDIA_BASE_URL=https://integrate.api.nvidia.com/v1
export NVIDIA_MODEL=YOUR_ACCESSIBLE_MODEL_ID
IFS= read -r -s -p 'NVIDIA API key: ' NVIDIA_API_KEY; printf '\n'
export NVIDIA_API_KEY
.venv/bin/python run.py --destination phoenix --output /tmp/relay-triage --verify
```

The runner uses real SDK scopes and a real model request. It validates the handoff,
local event parentage, and Phoenix delivery. It preserves failed runs for inspection.
For a hosted destination, use that recipe's environment variables and
`--destination langsmith`, `weave`, or `datadog`; `--verify` is Phoenix-specific.

From your local computer, forward the Phoenix UI:

```bash
brev port-forward YOUR_INSTANCE --port 6006:6006
```

Open `http://localhost:6006`. Use `--host` only if both services run on a reachable
Brev VM host rather than its workspace container.
</Accordion>

<Accordion title="Brev alternative: use Hermes">
Install and authenticate a Hermes build with native Relay support using the
[Hermes quickstart](/getting-started/quick-start/hermes). In the same example directory:

```bash
hermes doctor
python3.12 run.py --harness hermes --destination phoenix --output /tmp/relay-hermes --verify
```

Hermes manages its own Relay dependency. Check the NeMo Relay Plugins section
of `hermes doctor` before running.
</Accordion>

## 4. Verify capture and destination delivery

Accept the integration when all these checks pass:

| Check | Evidence |
| --- | --- |
| Correct destination | The intended project and service contain the run at its recorded time. |
| Captured activity | Expected agent or turn, LLM, and tool spans exist for the chosen capture path. |
| Correlation | Observed calls share the trace and have the expected parents; exported parents are present. |
| Useful fields | Model identity and usage appear when the capture path supplies them. |
| Privacy | Restricted payloads are absent or redacted according to the approved policy. |

Local ATOF records prove capture. Inspect the destination tree to prove delivery;
an HTTP success or a closed model scope alone is insufficient.

<Accordion title="Brev example: verify synthetic redaction">
Use only the supplied synthetic fixture. This second run explicitly enables
payloads and an email redaction profile:

```bash
.venv/bin/python run.py --destination phoenix --output /tmp/relay-triage-redacted --redaction-demo --verify
```

The runner checks that the synthetic contact is absent from emitted payloads.
The source file and provider conversation retain it; redaction affects telemetry.
</Accordion>

### Reference trace

The instrumented Python workload delivered four correlated spans to Phoenix:

```text
support-triage                       AGENT
├─ read_file                         TOOL
├─ openai.chat_completions            LLM
└─ write_file                        TOOL
```

The metadata-only and synthetic-redaction runs both passed local parentage and
Phoenix delivery checks. The redaction run also confirmed that the synthetic
contact was absent from emitted payloads.

A Hermes run exported 12 spans, including a session, turn, logical-call parents,
four model calls, and two tools. Counts depend on the workload and capture path.
Hosted-platform export checks establish request contracts; confirm authenticated
delivery in your destination.

## Cleanup and next steps

Stop the disposable Phoenix process and retain any evidence you need before
removing your chosen output directories and virtual environment. Leave shared
collectors and other users' configurations running.

Apply the same exporter settings to your chosen capture path. Use
[exporter diagnostics](/configure-plugins/observability/configuration) to distinguish
capture gaps, authentication failures, and delivery problems.
