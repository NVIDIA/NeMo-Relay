A managed tool callback and every execution-intercept continuation return one
canonical application-visible result:

```json
{
  "result": {}
}
```

`result` is required and contains the application-owned tool payload.
`annotation` is optional opaque adjacent metadata. It can be any JSON value.
An absent or JSON `null` annotation means that the result has no annotation; an
empty object (`{}`) is a present annotation.
Relay transports the annotation without interpreting its schema.

A tool execution intercept wraps or short-circuits that callback and returns a
canonical outcome:

```json
{
  "result": {},
  "annotation": {"source": "cache"},
  "pending_marks": []
}
```

`result` and `annotation` form the application-visible result passed to the
remaining middleware. `pending_marks` defaults to an empty list and remains
Relay-owned lifecycle data. Each pending mark contains `name`, optional
`category` and `category_profile`, and optional `data`, `data_schema`,
`metadata`, and typed log `severity`. Relay assigns event UUIDs, parent UUIDs,
and timestamps.

## Continuation Semantics

The default tool callback and an intercept's `next(args)` continuation both
return `ToolExecutionResult`. The continuation exposes the downstream `result`
and `annotation`, but not downstream pending marks. An intercept can preserve,
replace, or remove the annotation in its returned outcome. Relay retains
pending marks separately, combines them in effective middleware order, and
materializes them only after the final outcome succeeds.

Use the existing global, scope-local, or plugin-context tool execution
registration APIs to produce pending marks, and return the canonical outcome
from every registered callback. Use a
[mark event sanitizer](/reference/event-sanitizers) when the emitted pending
mark's `data`, `category_profile`, or `metadata` must be sanitized. Public APIs,
native `v1.0` plugins, and `nvidia.nemo.relay.worker.v1` workers require canonical
tool callback and intercept returns.

## Event and Exporter Projection

For a successful tool end event, Relay records `result` as the event output and
places a non-null annotation at
`category_profile.tool_result_annotation`. Tool sanitize-response guardrails
receive and sanitize only `result`. They cannot read or rewrite the annotation.
The scope-end event sanitizer runs after the tool response sanitizer and can
replace or remove `category_profile.tool_result_annotation` before subscribers
or exporters receive the event.

ATOF preserves the annotation in the tool end event's category profile. ATIF
places it in the observation result's `extra.tool_result_annotation` field.
The `full` and `openinference` OpenTelemetry projections serialize it as one
opaque JSON-valued `nemo_relay.tool.result.annotation` attribute rather than
flattening application-defined keys. The standards-only `gen_ai` projection
does not emit Relay-private attributes.

Relay returns the unsanitized `ToolExecutionResult` to the application. Event
sanitizers affect observability only.

## Normalized Tool Results

Framework integrations can use one JSON format for tool results. This wrapper
holds the display content, a failure flag, and the encoded result. Store it in
`ToolExecutionResult.result`. The following example shows its fields:

```json
{
  "schema": "nemo.relay.tool_result@1",
  "content": "The tool's answer",
  "is_error": false,
  "result": {"framework_owned": "payload"}
}
```

All four fields are required:

| Field | Meaning |
| --- | --- |
| `schema` | The format name and version. Use `nemo.relay.tool_result@1`. |
| `content` | Display text, an array of content parts, or `null` when there is no display content. |
| `is_error` | `true` if the tool returned a failure result. Otherwise, use `false`. |
| `result` | The JSON value that the codec uses to restore the original tool result. |

The wrapper can also include a `cache` object. Set `cache.replayable` to `true`
only when the codec can restore the result in a later call. The codec can keep
source call IDs in this object. It must bind the restored result to the new
call. A result that needs objects from the original call must set
`cache.replayable` to `false`.

This flag does not enable caching. The tool must also meet the
[cache policy](/configure-plugins/adaptive/response-cache#tool-result-cache).
The built-in cache does not store or replay wrappers unless
`cache.replayable` is `true`.

Relay reads the content and failure flag only when the wrapper has the expected
schema and field types. Other JSON values pass through unchanged. The optional
`ToolExecutionResult.annotation` field stays separate. Relay copies that field
without reading its contents.

Tool end events include the full wrapper. ATIF uses `content` for the
observation when it can represent the text or image parts. It keeps the full
wrapper in `extra.tool_result`. For failed results, ATIF also adds
`extra.is_error: true`. Successful results omit this flag.

When `is_error` is `true`, Relay sets `otel.status_code` to `ERROR` for the tool
span. This applies to both managed and manual tool end helpers. The tool still
returns its result. Relay does not raise an exception or emit an exception
event for this handled failure.

Tool response sanitizers receive the full wrapper. Event sanitizers can still
change or remove fields before export.

Execution intercepts can pass the wrapper through or edit its content and
failure flag. For LangChain and LangGraph, the codec applies these edits to the
matching `ToolMessage`. It keeps the message's other fields and the graph state.
For Google ADK, edit the wrapper's `content` and `is_error` fields. Set
`is_error` to `true` for a failure or `false` for success. Relay updates the
ADK result to match these fields.

Choose `content` based on the tool's result type:

| Result Type | Set Wrapper `content` To | How ADK Receives the Edit |
| --- | --- | --- |
| Text or an object with text | The output text | A failure has an `error` entry. A successful result has no `error` entry. |
| MCP tool result | The content blocks | The content blocks and an `isError` flag that matches wrapper `is_error`. |
| Code execution | The output text | `stdout` for success or `stderr` for failure, or `output` and a matching `outcome`, depending on the result type. |
| Other structured data, such as a list or dictionary | Valid JSON text | The parsed JSON. For a failure, include a nonempty `error` value in the JSON. |

A failed result needs error text. For structured data, the JSON content must
agree with the failure flag. For example, `{"error": "blocked"}` is valid
content when `is_error` is `true`. An invalid edit fails the call.

If an intercept returns a cached result without calling the tool, it must
return the full wrapper for that framework's codec.

The LangChain and LangGraph tool codec writes each value in `result` with its
type. The same tool result always gives the same JSON. Subscribers and
intercepts can read every field that has a JSON form.

A later call can restore built-in Python values, standard framework messages,
commands, and graph destinations. On replay, the codec binds matching tool
messages to the current tool-call ID. It clears their old graph message IDs so
the graph can assign new ones. Other messages keep their IDs.

Other Python objects, such as custom message subclasses, artifacts, and state
objects, stay with the call that returned them. Their JSON shows type and data.
Parts with no JSON form show only a type name. These results are not
replayable. The built-in cache runs the tool again instead of reusing them.

An intercept can edit `result` during the call. The codec rebuilds each changed
value with its type and keeps unchanged objects. Parts with no JSON form must
stay unchanged.

JSON cannot hold some Python values exactly. The codec records these values in
`result` with their own kinds. In `content` and in readable JSON of other
objects, NaN and infinity appear as `null`. Integers outside the 64-bit range
appear as decimal text. Lone surrogate characters appear as U+FFFD. When an
intercept leaves these parts unchanged, the tool and framework receive the
original values.

## Managed Lifecycle

On successful managed execution, Relay emits the tool end event before any
pending marks. The end timestamp is no earlier than one microsecond after the
tool start timestamp. Relay emits pending marks in their resolved middleware
order, assigns each mark the managed tool UUID as its parent, and gives each
mark a timestamp after the tool end event.

If execution or an intercept fails, Relay emits the error end event without a
tool result annotation and discards accumulated pending marks. Pending marks
are never included in the application-visible tool result or passed to tool
sanitize-response guardrails. They pass through the mark sanitizer registry
when materialized.

## Tool Execution Context

Beginning with Relay 0.9, every tool execution intercept receives the tool
call's context instead of separate tool-name and argument parameters. The
context carries the following fields:

| Field | Description |
| --- | --- |
| `tool_name` | Name of the tool being executed. |
| `args` | JSON argument payload entering this intercept. |
| `tool_call_id` | Provider-issued correlation identifier recorded on the managed tool call, or absent when the call did not record one. |
| `execution_context` | Optional application-supplied JSON object for execution intercepts. See [Application Execution Context](#application-execution-context) for its scope and trust requirements. |

`tool_call_id` is the same identifier that Relay records on tool lifecycle
events. An intercept that completes execution itself, without invoking the
remaining chain, uses it to associate its result with the originating tool
call.

The existing registration names now use the context callback. Scope-local and
plugin-context registrations follow the same naming.

| Surface | Registration |
| --- | --- |
| Python | `register_tool_execution(name, priority, fn)` |
| Rust | `register_tool_execution_intercept` |
| Go | `RegisterToolExecutionIntercept` |
| Node.js | `registerToolExecutionIntercept` |
| Public C | `nemo_relay_register_tool_execution_intercept` |
| Worker v1 SDKs | `register_tool_execution_intercept` |

The callback takes two parameters because the tool name and arguments move
onto the context:

```python
from collections.abc import Awaitable, Callable

import nemo_relay
from nemo_relay import Json, ToolExecutionContext, ToolExecutionInterceptOutcome, ToolExecutionResult

async def measure(
    context: ToolExecutionContext,
    next_call: Callable[[Json], Awaitable[ToolExecutionResult[Json]]],
) -> ToolExecutionInterceptOutcome:
    downstream = await next_call(context.args)
    record(context.tool_call_id, context.tool_name, downstream.result)
    return ToolExecutionInterceptOutcome(result=downstream.result)

nemo_relay.intercepts.register_tool_execution("measure", 10, measure)
```

```javascript
registerToolExecutionIntercept('measure', 10, async (context, next) => {
  const downstream = await next(context.args);
  record(context.toolCallId, context.toolName, downstream.result);
  return { result: downstream.result };
});
```

Rust, Python, and Go execution intercepts receive `(context, next)`. In Node.js the
context object uses `toolName`, `args`, and `toolCallId`, where
`toolCallId` is `string | null`. The public C callback receives a single
`context_json` string carrying `tool_name`, `args`, and `tool_call_id`;
callbacks must ignore unknown fields. The typed worker protocol carries the
optional `tool_call_id` in `ToolExecutionInvocation`.

### Application Execution Context

An application can adopt execution middleware incrementally while retaining its
existing human approval flow. For example, it can supply a reference to a
completed application review separately from the tool's business arguments. A
middleware component that understands that review can avoid repeating its own
review, then call `next` so the remaining middleware and tool callback still run.
Relay does not interpret the reference or change the approval flow itself.

The application APIs carry the same optional value through each binding:

| Binding | Supply context when executing | Read it in execution middleware |
| --- | --- | --- |
| Rust | `ToolCallExecuteParams::builder().execution_context(value)` | `context.execution_context()` |
| Python | `tools.execute(..., execution_context=value)` | `context.execution_context` |
| Node.js | `executionContext` in `typedToolExecute` options | `context.executionContext` |
| Go | `WithToolExecutionContext(value)` on `ToolCallExecute` or `tools.Execute` | `context.ExecutionContext` (`json.RawMessage`) |
| C | `execution_context_json` on `nemo_relay_tool_call_execute_with_context` | Optional `execution_context` property in the callback's context JSON |

Rust and Python worker SDKs expose the same optional context on their tool
execution callback. The C entry point is additive: existing execute functions
retain their signatures and omit context. Go rejects the option on manual
`ToolCall` and `ToolCallEnd`, where execution middleware does not run.

The value must be a JSON object with a serialized UTF-8 size of at most 16 KiB
and at most **64 nested container levels**. The root object counts as level 1;
each nested object or array adds one level, while scalar values add none.
The host rejects deeper values before invoking middleware. This limit leaves
headroom under the Rust worker decoder's recursion protection.
Keys and nested values belong to the application; Relay defines no approval
schema or reserved application keys. Omission means no context, whereas `{}`
is a supplied, empty context. Invalid values fail before tool execution.

This field has a narrower lifetime and audience than event metadata:

- Only execution intercepts receive it. Tool arguments, request intercepts,
  conditional guardrails, and the final tool callback do not receive it as a
  separate parameter.
- Each intercept receives an isolated snapshot. Changes to a binding-local
  object do not change what another intercept sees. Calling `next` can rewrite
  business arguments, but cannot replace the execution context.
- A nested managed tool call has no execution context unless its caller supplies
  one explicitly. Scope metadata does not populate it automatically.
- Relay does not automatically copy it to lifecycle events, results,
  annotations, or telemetry. Application and plugin code can still disclose it
  explicitly, so avoid logging it or adding credentials to it.

Application-supplied does **not** mean verified authorization. Relay does not
verify a human decision, caller identity, signature, expiry, or operation binding
inside this object. The application must validate its own approval proof and
bind it to the exact tool, business arguments, owner and applicable policy before
supplying a review claim. Do not populate it from a model-generated `approved`
flag. An intercept must also check that the claim still covers its current
arguments, because earlier middleware may have rewritten them. Missing,
unrecognized or mismatched claims should use that component's normal review
path; they must not imply approval. The application must stop a human-denied
operation rather than ask middleware to override that denial. If human approval
is mandatory and the operation changes, the application must reject it or obtain
fresh approval; a component's automated review does not renew human consent.

The following integration sketch keeps those application-specific checks
explicit. `validate_existing_approval`, `approval_covers_call` and
`perform_component_review` are application-defined functions; Relay does not
implement them or prescribe the proof format.

```python
import nemo_relay
from nemo_relay import tools


async def execute_after_application_approval(name, args, receipt, implementation):
    # Raise unless the real receipt approves this owner and exact operation,
    # remains valid, and satisfies the application's current policy.
    reviewed = validate_existing_approval(receipt, name, args)

    async def execute_reviewed(actual_args):
        # Later middleware can rewrite arguments. Revalidate at the actual
        # execution boundary; automated review cannot expand human consent.
        validate_existing_approval(receipt, name, actual_args)
        return await implementation(actual_args)

    return await tools.execute(
        name,
        args,
        execute_reviewed,
        execution_context={"application_review": reviewed},
    )


async def review(context, next_call):
    supplied = context.execution_context or {}
    if not approval_covers_call(
        supplied.get("application_review"), context.tool_name, context.args
    ):
        # This function must raise or deny when its policy does not allow the call.
        await perform_component_review(context.tool_name, context.args)

    # Skip only this component's repeated review, never the remaining chain.
    downstream = await next_call(context.args)
    return nemo_relay.ToolExecutionInterceptOutcome(
        result=downstream.result, annotation=downstream.annotation
    )


nemo_relay.intercepts.register_tool_execution("application-review", 10, review)
```

#### Transport Compatibility

**Application-side compatibility checks**

Node.js exposes a support helper because an older JavaScript typed wrapper can
silently ignore an unfamiliar `executionContext` options property. If your
application calls Relay through Node.js, check the helper for the API you use
before relying on that field:

- **Typed API (`nemo-relay-node/typed`):** check that its
  [`supportsToolExecutionContext()` helper](https://github.com/NVIDIA/NeMo-Relay/blob/ccff24e06239fd7b4379872dc4d064cab3bf3a3c/crates/node/ts/typed.ts#L43)
  exists and returns `true`. It checks both the typed wrapper and the compiled
  native binding, so a separate native-helper check is unnecessary.
- **Low-level API (`nemo-relay-node`):** check that its
  [`supportsToolExecutionContext()` helper](https://github.com/NVIDIA/NeMo-Relay/blob/ccff24e06239fd7b4379872dc4d064cab3bf3a3c/crates/node/src/api/mod.rs#L2015)
  exists and returns `true`.

Treat a missing helper, `false` result or error as unsupported. These queries
perform no tool call and only check the application's Node wrapper/native
binding support. They do not verify remote worker support, application approval
proofs or permission to execute.

Python, Rust, Go and C do not need an equivalent application-side helper for this API:

- **Python:** `tools.execute(..., execution_context=...)` uses an explicit
  keyword parameter. An older API without that parameter raises `TypeError`
  rather than silently ignoring it.
- **Rust:** the execution-context builder method and fields are checked at
  compile time. Code using them does not compile against an older API that
  lacks them.
- **Go:** the new option is checked at compile time, and its CGo bridge links
  against the new C export. An older source binding or native library cannot
  silently accept and discard this option.
- **C:** use the new declaration in the generated header and link against a
  library exporting `nemo_relay_tool_call_execute_with_context`. Existing
  execute symbols remain available; they do not accept context.

These language-level checks do not establish remote worker support. That is
checked separately through the worker handshake described below.

**Worker-side compatibility checks**

Omitting the field preserves existing calls and callback signatures. Receiving
it requires an updated binding or worker SDK. Workers advertise the
`tool-execution-context-v1` capability; a host rejects a context-bearing call
before invoking a worker intercept that does not advertise support. Calls
without execution context continue to support legacy workers. The capability
indicates transport support, not permission to execute.

The native dynamic-plugin `v1.0` ABI remains frozen and cannot carry this field.
A context-bearing call that reaches a legacy native tool execution intercept
fails explicitly instead of silently dropping its context. That frozen plugin
ABI is separate from ordinary Rust callbacks and the C JSON callback bridge.
C-registered execution intercepts, including Go intercepts using that bridge,
receive the same execution context through the extensible JSON envelope.

## Binding Contract

Managed callbacks, continuations, and execute helpers use the same logical
result in their native type or object shape:

| Surface | Managed Callback or Continuation Result |
| --- | --- |
| Python | `ToolExecutionResult(result, annotation=None)` |
| Rust | `ToolExecutionResult { result, annotation }` and its constructors |
| Go | `ToolExecutionResult { Result, Annotation }` |
| Node.js | `{ result, annotation? }` |
| Public C | Canonical JSON with required `result` and optional `annotation` |

Execution intercepts add lifecycle-owned pending marks to that shape:

| Surface | Execution-intercept Outcome |
| --- | --- |
| Python | `ToolExecutionInterceptOutcome` |
| Rust and native `v1.0` SDK | `ToolExecutionInterceptOutcome` |
| Go | `ToolExecutionInterceptOutcome` |
| Node.js | `{ result, annotation?, pendingMarks? }`; JavaScript pending-mark DTOs use `categoryProfile` |
| Public C | Canonical JSON with `result`, optional `annotation`, and optional `pending_marks` |
| Worker v1 SDKs | Protobuf `ToolExecutionResult` and `ToolExecutionInterceptOutcome`; arbitrary JSON fields use lossless `JsonValue` wrappers |

Canonical JSON uses `annotation`, `pending_marks`, and `category_profile`
across bindings.

Native plugins declare `compat.native_api = "v1.0"`. Their build SDK sets the
minimum host contract they require. The `compat.relay` range selects supported
Relay releases. Refer to [Native ABI Reference](/build-plugins/native/native-abi-reference).
Workers use `nvidia.nemo.relay.worker.v1`, contract version `1.0.0`.

## Return-Shape Errors

Python distinguishes `ToolExecutionResult` from
`ToolExecutionInterceptOutcome`. A callback that returns a raw dictionary is
rejected; return `ToolExecutionResult(payload)` instead. A forwarding intercept
must unwrap the downstream result:

```python
downstream = await next(args)
return ToolExecutionInterceptOutcome(
    result=downstream.result,
    annotation=downstream.annotation,
)
```

Do not pass `downstream` itself as the outcome result or return it directly.
The resulting `RuntimeError` names the required wrapper and this unwrapping
form.

Node.js represents both values as compatible object shapes. Therefore,
`return await next(args)` is a valid forwarding intercept in Node.js. Raw tool
callback returns and raw intercept outcomes are rejected with guidance to
return `{ result: payload }` or
`{ result: downstream.result, annotation: downstream.annotation }`.

LLM request intercepts use a different outcome because they must preserve an
annotated request and codec authority. That contract is described in [LLM
Request Intercept Outcomes](/reference/llm-request-intercept-outcomes). Worker
authors can refer to both outcome types in the [gRPC protocol reference](/build-plugins/workers/grpc-v1-protocol).
