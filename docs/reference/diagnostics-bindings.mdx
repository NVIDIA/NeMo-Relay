## Embedded Language Runtimes

Existing `plugin.initialize` entry points in Rust, Python, Node.js, and experimental
Go/C resolve a diagnostics service before plugin validation and activation. Configure
it through the existing `plugins.toml` resolver, including the existing explicit-file
argument. No diagnostics setup call, CLI configuration discovery, listener, exporter,
or per-framework adapter is required.

```toml
# plugins.toml: uses the existing user/explicit and system file layers.
[diagnostics]
enabled = true

[diagnostics.limits]
max_events = 256
max_snapshot_bytes = 131072
```

File layers merge field by field in the existing resolver's order. An omitted
programmatic `diagnostics` field inherits that profile. A supplied programmatic
profile replaces the complete resolved service profile; unspecified fields use
core defaults. These service settings stay out of plugin component configuration,
execution fingerprints, and legacy plugin reports. Invalid settings fail startup
without selecting a fallback profile. `validate` checks the profile without
starting the service.

The first initialization selects the process-owned service, enabled or disabled.
Repeated initialization with equivalent settings reuses it. Changed settings return
`diagnostics: configuration_conflict`; the selected context and existing activation
remain intact. Change service settings by restarting the process. Plugin failure,
close, replacement, and reload do not erase the service or its lifetime counters.
The service does not keep the process alive and does not persist evidence after exit.

Python import and Node environment registration preserve their existing logging
behavior without consuming an unselected diagnostic default. When the service
starts, a Relay-owned default logger attaches once using its existing sinks, queues,
and rate limits. It does not replay pre-startup log records. Application-owned
loggers are preserved; reader metadata reports logging coverage separately. Node
runtime environments share the service; unloading one does not close another's
logger. Inherited diagnostic handles after `fork` return `fork_requires_exec`
before acquiring service locks; start a fresh executable process before using them.

### Optional Readers

Readers are explicit authority to inspect bounded, potentially unsanitized detail.
Query selectors do not restrict that authority: snapshots also contain context-wide
totals. Applications serving readers to other clients must provide authorization.
Snapshots never enter event subscribers, exporters, legacy reports, automatic
exception attachments, or operational logging. OTel integration remains deferred.
Custom component/recorder authoring is available through the Rust API only.
The [recording and classifier guide](/reference/diagnostics) describes the Rust
producer APIs.

The supported embedded reader operations are:

| Operation | Python | Node.js | Rust embedded adapter |
| --- | --- | --- | --- |
| Obtain an existing service reader | `diagnostics.reader()` | `diagnostics.reader()` | `embedded::reader()` |
| Capture with a native query | `reader.snapshot(query)` | `reader.snapshot(query)` | `reader.snapshot(&query)` |
| Capture canonical JSON | `reader.snapshot_json(query)` | `reader.snapshotJson(query)` | `reader.snapshot_json(query_json)` |
| Inspect budgets, occupancy, and logging coverage | `reader.info()` | `reader.info()` | `reader.info()` |
| Release a reader or page | Release Python references | Release JavaScript references | Drop the reader or page |

Python returns caller-owned dictionaries with canonical `snake_case` keys and
Python `int` diagnostic integers. Node.js returns caller-owned `camelCase` objects
and `bigint` diagnostic integers. For entry/component accounting and resource
context, use the
[memory reader operations](/reference/diagnostics-memory#detailed-memory-inspection).
These representations also apply to memory pages and aggregate memory gauges.
Rust returns an adapter-owned canonical page;
`page.as_str()` borrows it, and `serde_json::from_str::<DiagnosticSnapshot>()`
decodes a separate caller-owned value. Drop each Rust page after use to return its
copy permit. Dropping a reader does not stop the service in any binding.

### Startup, Snapshots, and Metadata

These examples use a complete programmatic diagnostics profile. Omit it to use
the existing file resolver. `validate` checks the selected host profile without
starting the service; `initialize` selects the process service. The exact plugin
validation APIs accept component configuration only and reject a top-level
`diagnostics` field. Use ordinary host `validate` for service settings.

<Tabs>
<Tab title="Python" language="python">
```python
import json
from nemo_relay import diagnostics, plugin

async def inspect_runtime():
    config = plugin.PluginConfig(diagnostics={"enabled": True})
    plugin.validate(config)
    activation = await plugin.initialize(config)
    try:
        reader = diagnostics.reader()  # Does not start or enable collection.
        page = reader.snapshot({"component_key": "logging"})
        failures = page["lifetime"]["totals"]["failures_total"]["value"]
        assert type(failures) is int
        wire = json.loads(reader.snapshot_json())
        assert isinstance(wire["sequence"], str)
        info = reader.info()
        reserved = info["binding_reserved_bytes"]
        logging_coverage = info["logging_coverage"]
        # Inspect these values only inside the authorized application boundary.
    finally:
        await activation.close()
    final_page = reader.snapshot()  # The service outlives this activation.
```
</Tab>

    diagnostics::{DiagnosticQuery, DiagnosticSnapshot, DiagnosticsSettings, embedded},

let config = PluginHostConfig {

let reader = embedded::reader()?;

let failures: u64 = snapshot.lifetime.totals.failures_total.value.get();

let info = reader.info()?;
let reserved = info.binding_reserved_bytes;
let logging_coverage = info.logging_coverage;
activation.close()?;
let final_page = reader.snapshot_json("{}")?; // Same process-owned service.

`JSON.stringify` cannot serialize Node's native `bigint` view. Use `snapshotJson()`
for portable serialization. Use `inspectMemoryJson()` for the memory view. Canonical JSON keeps `snake_case` keys and lossless
64-bit decimal-string integers in every language. Native query helpers accept
Python integers or Node `bigint` at u64 positions, such as `after_sequence` or
`afterSequence`; Node rejects JavaScript `number` substitutes there. Row caps such
as `max_events`/`maxEvents` remain ordinary small integers. Rust uses
`DiagnosticNumber` at u64 query positions. Unknown code, failure-class, execution,
and phase names stay strings. Saturation markers and optional unavailable values
are preserved.

### Bounded Pagination

A snapshot is one page. Keep the query selectors unchanged and pass the returned
opaque `continuation` to the next call. Native continuations can be passed directly
back to their binding; do not convert Node `bigint` cursor fields to `number`.
A cursor refers to the same source revision and selection. If evidence changes,
`invalid_cursor` means the caller must decide whether to restart from the first
page with a fresh caller budget. Reads reset no counters. Lifetime totals remain
context-wide and cumulative on every page; do not sum them across pages.

The examples below limit the caller to 32 pages and consume each page immediately.
The runnable examples report page-budget exhaustion explicitly. In a live service,
also handle `busy` and `invalid_cursor` using the error contract below.

<Tabs>
<Tab title="Python" language="python">
```python
query = {"max_components": 1, "max_events": 1}
for _ in range(32):
    page = reader.snapshot(query)
    # Inspect page["components"] and page["events"] within the authorized boundary.
    if page["continuation"] is None:
        break
    query["continuation"] = page["continuation"]
else:
    raise RuntimeError("The caller's page budget was exhausted")
```
</Tab>

<Tab title="Node.js" language="node">
```javascript
const query = { maxComponents: 1, maxEvents: 1 };
let complete = false;
for (let remaining = 32; remaining > 0; --remaining) {
  const page = reader.snapshot(query);
  // Inspect page.components and page.events within the authorized boundary.
  if (page.continuation === null) {
    complete = true;
    break;
  }
  query.continuation = page.continuation;
}
if (!complete) throw new Error("The caller's page budget was exhausted");
```
</Tab>

<Tab title="Rust" language="rust">
```rust
let mut query = DiagnosticQuery {
    max_components: Some(1),
    max_events: Some(1),
    ..Default::default()
};
let mut complete = false;
for _ in 0..32 {
    let page = reader.snapshot(&query)?;
    let snapshot: DiagnosticSnapshot = serde_json::from_str(page.as_str())?;
    // Inspect snapshot.components and snapshot.events within the authorized boundary.
    query.continuation = snapshot.continuation;
    if query.continuation.is_none() {
        complete = true;
        break;
    }
} // Each page's adapter permit is returned on drop.
if !complete {
    return Err("The caller's page budget was exhausted".into());
}
```

### Handling Reader Errors

Branch on stable reasons rather than exception text. A reader error contains no
query text or retained detail. This invalid-query example demonstrates the error
surface without logging any snapshot.

<Tabs>
<Tab title="Python" language="python">
```python
try:
    reader.snapshot({"unknown": True})
except diagnostics.DiagnosticsError as error:
    if error.reason != "invalid_query":
        raise
```
</Tab>

<Tab title="Node.js" language="node">
```javascript
try {
  reader.snapshot({ unknown: true });
} catch (error) {
  if (!(error instanceof diagnostics.DiagnosticsError) || error.reason !== 'invalid_query') {
    throw error;
  }
}
```
</Tab>

<Tab title="Rust" language="rust">
```rust
match reader.snapshot_json(r#"{"unknown":true}"#) {
    Err(error) if error.reason() == "invalid_query" => {}
    Err(error) => return Err(error.into()),
    Ok(_) => return Err("An unknown query field was accepted".into()),
}
```
</Tab>
</Tabs>

### Experimental Go and C Readers

Experimental Go callers set `PluginConfig.Diagnostics`, then call
`ReadDiagnostics()`, `Snapshot(DiagnosticQuery{})`, `SnapshotJSON`, `InspectMemory`,
`InspectMemoryJSON`, and `Close`.
`DiagnosticNumber` has an underlying `uint64` and a checked decimal-string JSON
codec. Closing a reader only releases that reader; it does not stop the service.

Experimental C callers use `nemo_relay_diagnostics_reader`,
`nemo_relay_diagnostics_snapshot_json`, `nemo_relay_diagnostics_memory_json`,
`nemo_relay_diagnostics_info_json`, and
`nemo_relay_diagnostics_reader_free`. Successful strings are caller-owned and
released with `nemo_relay_string_free`. Failed output pointers are null. Callers
must provide live, valid, non-aliasing storage and keep the native library loaded;
the ABI cannot identify arbitrary freed or forged pointers. Reader free must not
race a read.

### Availability, Budgets, and Copy Ownership

`reader()` before configuration returns `not_initialized`, without creating a
disabled default. A configured disabled reader exposes metadata but snapshots
return `disabled`. Other stable reasons include `busy`, `query_disabled`,
`invalid_query`, `invalid_cursor`, `snapshot_capacity`, `unsupported_schema`, `allocation_failed`, and
`fork_requires_exec`. Python/Node helper errors expose `.reason`; Go returns
`*DiagnosticsError`; C uses existing status values plus the stable reason in
`nemo_relay_last_error`. No failure contains query text or retained detail.

`info()` (Go/C: `InfoJSON`/`nemo_relay_diagnostics_info_json`) reports core limits,
core memory occupancy, logging coverage, and the independent adapter budget:

| Resource | Bound |
| --- | --- |
| Encoded query | 4,096 UTF-8 bytes; unknown top-level fields rejected |
| Simultaneous snapshot/memory copies and conversions | Two per service, shared by all reader clones |
| Payload per copy | Configured core `max_snapshot_bytes` |
| Default copy reservation | 262,144 bytes: two 131,072-byte pages |
| Waiting queue | None; saturation returns `busy` |

Disabled services and services with `max_queries = 0` allocate no copy payload
buffers. Enabled services reserve the copy payloads during startup; those bytes
are additional to core `max_owned_bytes`.
A core query workspace is released after copying its bounded canonical page,
before any language object conversion. The adapter permit remains held through
conversion and is returned on success or error. Caller-retained JSON strings,
decoded graphs, Python/JavaScript object overhead, allocator metadata, and Go/C
result allocations are outside the retained service payload budgets. These
figures are not a whole-process working-set or RSS ceiling.

Reads are synchronous and bounded. They do not create background tasks or wait
queues. A reader does not reset counters, infer readiness, or supply an empty
snapshot when evidence is unavailable. The separate [memory view](/reference/diagnostics-memory#detailed-memory-inspection)
provides entry/component backing attribution and existing resource-sample context.
