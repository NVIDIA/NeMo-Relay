Configure `kind = "pii_redaction"` in `plugins.toml`. Use the reference tables to
look up settings, then use the [worked examples](#worked-examples) to compare
input event data with the published result. For runtime placement and the
middleware comparison, refer to [About](/configure-plugins/pii-redaction/about).

There are two supported configuration forms:

- **Profiles:** Define one or more policies under
  `[[components.config.profiles]]`. Every enabled profile covers all supported
  surfaces.
- **Single policy:** Omit `profiles` and define a policy directly under
  `[components.config]`. This form also provides surface flags.

## Configuration Reference

All configuration keys use `snake_case` in `plugins.toml` and every binding.
A field shown as **Unset** has no configured value.

### Component Shape

The plugin document has root `version = 1`. Each `[[components]]` entry uses:

| Setting | Type | Default | Description |
| --- | --- | --- | --- |
| `kind` | String | Required | Set to `pii_redaction`. |
| `enabled` | Boolean | `true` | Enable or disable the whole component. |

The following shared fields belong under `[components.config]` in either form:

| Setting | Type | Default | Description |
| --- | --- | --- | --- |
| `version` | Integer | `1` | PII redaction configuration schema version. |
| `codec` | String | Unset | Optional fallback API format for LLM calls that do not supply an active codec. For example, use `codec = "anthropic_messages"` for Anthropic Messages payloads. Omit this field when your integration supplies a codec; the call's active codec takes precedence. |
| `profiles` | Array of objects | Unset | Ordered policies. Omit to use the single-policy form. |
| `policy` | Object | See details | Handling of unknown components, unknown fields, and unsupported values. |

<details>
<summary>How to choose a codec</summary>

Choose the value by the API payload format:

| LLM API Format | `codec` Value |
| --- | --- |
| OpenAI Chat Completions | `openai_chat` |
| OpenAI Responses | `openai_responses` |
| Anthropic Messages | `anthropic_messages` |
| OCI Generative AI | `oci_genai` |
| Gemini GenerateContent | `gemini_generate_content` |

Omit `codec` when the managed call supplies an active codec. A configured value
is only a fallback for a call without one; it cannot override an active codec.
Request policies use the active codec's resolved decode/encode capability,
including runtime and opaque codecs. Normalized response projection requires a
recognized built-in codec because response codec capabilities are decode-only.

For a mixed-provider gateway, rely on the active codec of each call. The
[LLM request-only example](#targeting-and-composition) shows the selector boundary
for an OpenAI Chat Completions request.

</details>

<details>
<summary>Configuration validation policy</summary>

Set these fields under `[components.config.policy]` to control configuration
diagnostics. Each accepts `ignore`, `warn`, or `error`.

| Field | Default | Meaning |
| --- | --- | --- |
| `unknown_component` | `warn` | Handling of an unknown component kind. |
| `unknown_field` | `warn` | Handling of an unknown field on a known component. |
| `unsupported_value` | `error` | Handling of an unsupported value on a known field. |

The global plugin policy can also affect the resolved policy. Refer to
[Configure](/configure-plugins/plugin-configuration-files) for precedence.

</details>

### Profile Settings

These fields belong under each `[[components.config.profiles]]` entry:

| Setting | Type | Default | Description |
| --- | --- | --- | --- |
| `enabled` | Boolean | `true` | Enable or disable this entire policy. |
| `mode` | String | `builtin` | Backend: `builtin` or `local_model`. |
| `priority` | Integer | `100` | Execution order; lower values run first. |
| `builtin` | Object | Unset | Required for `mode = "builtin"`. See [Built-in Settings](#built-in-settings). |
| `local` | Object | Unset | Provider-specific settings for `local_model` mode; requires a runtime-installed provider. |

At least one profile must be enabled. Use either profiles or the
[single-policy settings](#single-policy-settings); do not combine the two forms.

<details>
<summary>How profiles compose and execute</summary>

Profiles execute by ascending `priority`, with array order breaking ties.
Relay assigns internal positional names such as `profile_0`; no user-supplied
ID is required. Disabled profiles are still validated, but do not register
callbacks. At least one profile must be enabled.

Each enabled profile covers all supported sanitization surfaces. Profiles do
not accept `input`, `output`, `mark`, `tool_input`, or `tool_output` flags.
Use the [single-policy form](#single-policy-settings) when you need those controls.

Profile lists concatenate during configuration layering, with higher-precedence
profiles placed before lower-precedence profiles. Refer to
[Configure](/configure-plugins/plugin-configuration-files) for file discovery
and merge rules.

</details>

<a id="built-in-mode" />

### Built-in Settings

Use `[components.config.profiles.builtin]` for a profile, or
`[components.config.builtin]` for a single policy. The shipped `builtin` backend
implements deterministic actions and detector presets.

| Setting | Type | Default | Description |
| --- | --- | --- | --- |
| `preset` | String | Unset | Set to `trajectory_context` for broad conversational-content removal while retaining supported analytics. |
| `action` | String | `remove` | `remove`, `redact`, `regex_replace`, `hash`, or `mask`. Choose an action explicitly, or use `preset`. |
| `target_paths` | Array of strings | `[]` | Exact RFC 6901 pointers. Combined with `target_path_globs`. |
| `target_path_globs` | Array of strings | `[]` | Pointer globs; each whole `*` segment matches one key or index. Recursive `**` is unsupported. |
| `pattern` | String | Unset | Regex matcher. Use either `pattern` or `detector`, never both. |
| `detector` | String | Unset | Built-in matcher such as `email` or `api_key`. See [Detector Presets](#detector-presets). |
| `replacement` | String | `[REDACTED]` | Replacement for `redact`, `regex_replace`, and `trajectory_context`. |
| `mask_char` | String | `*` | Masking token for `mask`. Must not be empty. |
| `unmasked_prefix` | Nonnegative integer | `0` or detector default | Leading characters preserved by `mask`. |
| `unmasked_suffix` | Nonnegative integer | `0` or detector default | Trailing characters preserved by `mask`. |
| `custom_mark_payload_policy` | String | `redact_all_leaves` | Trajectory preset only. `preserve` retains unknown custom marks from trusted producers. |
| `metric_string_attribute_allowlist` | Map of string arrays | `{}` | Trajectory preset only. Exact attribute names and bounded string values that typed metric marks may retain. |

<a id="requirements" />

<Note>
`remove` requires at least one selector. `redact` and `regex_replace` require
`pattern` or `detector`. For string actions, omitting both selector lists
selects every string leaf within each payload boundary. Selecting a container
with a string action does not select its descendant strings.

`trajectory_context` defines its own policy. Do not combine it with `action`,
`pattern`, `detector`, target selectors, or masking fields. It accepts
`replacement`, `custom_mark_payload_policy`, and
`metric_string_attribute_allowlist`.
</Note>

| Setting | Type | Default | Description |

| `priority` | Integer | `100` | Sanitizer priority; lower values run first. |
| `builtin` | Object | Unset | Required for `builtin` mode. |

| `input` | Boolean | `true` | Managed LLM request sanitization and scope-start processing. |
| `output` | Boolean | `true` | Managed LLM response sanitization and scope-end processing. |

<details>
<summary>How surface flags apply to scope events</summary>

Scope-start processing is enabled when either `input` or `tool_input` is `true`;
scope-end processing is enabled when either `output` or `tool_output` is `true`.
On LLM and tool events, metadata follows the corresponding LLM or tool flag.
Other scope categories use the enabled shared scope-start or scope-end hook.

</details>

## Detailed Behavior

### Action Semantics

<details>
<summary>How each action changes a selected value</summary>

#### `remove`

`remove` is structural.

Configure at least one `target_paths` or `target_path_globs` selector when
using `remove`. Relay rejects an unscoped `remove` policy during validation to
prevent accidental removal of every string value in the selected surfaces.

When a target matches:

- Object fields are removed.
- Array elements become `null` on JSON-native surfaces. If a normalized LLM
  array removal cannot be safely re-encoded, Relay omits the event payload and
  its annotation instead.
- Targeted scalar or root values become `null`.

#### `regex_replace`

`regex_replace` applies the configured regex to matching string leaves and
replaces matches with the configured `replacement`.

If you set `detector` instead of `pattern`, the built-in backend uses the
detector's stock matcher regex.

#### `redact`

`redact` is the deterministic whole-match replacement lane.

It uses the same `pattern` or `detector` matcher flow as `regex_replace`, but
defaults the replacement token to `[REDACTED]` and is intended for cases where
you do not want to preserve any matched secret characters.

Use `redact` when you want:

- credential-style secrets fully replaced
- a consistent redaction token across detectors
- clearer policy intent than a custom `regex_replace`

#### `hash`

`hash` replaces matching string leaves with their SHA-256 hex digest.

When `pattern` or `detector` is set, `hash` only replaces the matching
substring instead of hashing the entire string leaf.

#### `mask`

`mask` replaces the middle portion of each matching string leaf with the
configured `mask_char`.

Use `unmasked_prefix` and `unmasked_suffix` when you want to preserve a small
leading or trailing segment for correlation or debugging, such as the last four
characters of a token.

When `pattern` or `detector` is set, `mask` only masks matching substrings
inside the string leaf.

When `detector` is set and you do not specify `unmasked_prefix` or
`unmasked_suffix`, the built-in backend applies detector-aware defaults:

- `email`: Preserves the domain and the first local-part character
- `phone`: Preserves the last four digits while keeping separators intact
- `api_key`: Preserves the vendor-style prefix such as `sk-` and the last four characters
- `ip_address`: Preserves the last octet
- `ipv6`: Preserves the last segment
- `url`: Preserves the scheme and host, then collapses the path/query tail
- `uuid`: Preserves the last four characters
- `bearer_token`: Preserves the auth scheme and the last four characters
- `jwt`: Preserves the header segment and the tail of the signature
- `credit_card`: Preserves the last four digits while keeping separators intact
- `aws_access_key_id`: Preserves the provider prefix and the last four characters
- `aws_secret_access_key`: Preserves the last four characters
- `gcp_api_key`: Preserves the `AIza`-style prefix and the last four characters
- `azure_storage_account_key`: Preserves the last four characters

</details>

### Detector Presets

<details>
<summary>Supported detectors and matching rules</summary>

The built-in detector presets are grouped into three deterministic families:

**Common PII**

- `email`
- `phone`
- `ip_address`
- `ipv6`
- `url`

**Structured Secrets**

- `api_key`
- `uuid`
- `bearer_token`
- `jwt`
- `credit_card`

`bearer_token` is heuristic rather than vendor-specific. It can still match
benign bearer-style values, so prefer a narrower detector when you know the
credential family.

**Cloud Credentials**

- `aws_access_key_id`
- `aws_secret_access_key`
- `gcp_api_key`
- `azure_storage_account_key`

They are deterministic regex-backed helpers, not model inference.

For actions other than `remove`, if both target-selector lists are empty, the
built-in backend sanitizes every matching string leaf in the selected payload
boundary. The `remove` action requires at least one selector.

</details>

### Observability Semantics

<details>
<summary>Payload boundaries and event publication</summary>

The plugin uses different payload boundaries for tools and LLMs:

- Tools use JSON-native payloads. Paths point into the emitted tool args
  directly. For built-in action policies, including detector-backed policies,
  tool response paths apply independently to the emitted
  `ToolExecutionResult.result` and `ToolExecutionResult.annotation` JSON
  documents. A path is relative to each document; it does not start with
  `/result` or `/annotation`.
- LLM requests use the active resolved codec for that managed call. LLM
  responses use the active built-in codec for normalized projection. Prefer
  normalized Relay paths such as:
  - `/headers/authorization` for an exact request header field
  - `/messages/0/content` for request message content
  - `/message` for the normalized assistant response text
- Marks and non-tool, non-LLM scopes sanitize `data`, `category_profile`, and
  `metadata` as separate JSON values. A target path is evaluated independently
  inside each value; it does not start with `/data`, `/category_profile`, or
  `/metadata`.

The current implementation also preserves provider-shaped response-path
compatibility for the supported built-in codecs, but normalized LLM paths are
the recommended contract for new configuration. If normalized paths are
configured and Relay cannot resolve a request codec or cannot project a
response through a recognized built-in or compatible fallback codec, the LLM
event payload and its annotation are omitted rather than emitting unsanitized
content. In particular, a manual LLM call with normalized target selectors, no
active codec, and no configured `codec` fallback omits both the payload and its
annotation.

The built-in plugin uses sanitize guardrails and event sanitizers.

That means:

- The real provider request and response values are unchanged.
- The emitted NeMo Relay start, end, or mark event observability fields are
  sanitized.
- `annotated_response` is regenerated from the sanitized end-event payload when
  the active response codec can decode that payload.
- Subscribers and exporters consume only the sanitized canonical event stream.
  Each exporter can omit or transform fields as part of its normal projection,
  but raw values removed by the plugin do not bypass the sanitizer.

For built-in action policies, including detector-backed policies, the PII
redaction scope sanitizer leaves `data` and typed `category_profile` fields
unchanged on tool and LLM scope events because the specialized sanitizer already
owns that lifecycle boundary. It sanitizes `metadata` independently. When
`tool_output` is enabled, the tool scope-end sanitizer also sanitizes only
`category_profile.tool_result_annotation`; the other typed tool profile
fields remain unchanged. This prevents repeated hashing or masking. Other scope
categories use the shared scope-start and scope-end hooks described under
[Single-Policy Settings](#single-policy-settings).

</details>

### Path Semantics

<details>
<summary>Exact pointers, globs, and container selection</summary>

`target_paths` are exact RFC 6901 JSON-pointer matches. `target_path_globs`
adds a restricted, opt-in selector language: a whole `*` segment matches one
object key or array index. Exact paths and glob paths are combined.
Within `target_path_globs`, `*` is a wildcard only when it is the complete
pointer segment. Segments such as `content*` and `foo*bar` match those literal
object keys.

For example, these selectors cover every message and provider-output text
block without capping the number of array items:

```toml
target_path_globs = [
  "/messages/*/content/*/text",
  "/output/*/content/*/text",
]
```

For example, `/messages/*/content` matches both
`/messages/A/content` and `/messages/B/content`. If either `content` value is
an array or object, `redact` does not redact its descendant strings: it acts
only on selected string values. For content parts such as
`{"messages":[{"content":[{"text":"alice@example.com"}]}]}`, use
`/messages/*/content/*/text` to select the `text` string. The same glob also
matches a `text` key in an object one level below `content`.

Globs are not recursive: `/output/*` selects only a direct child of `output`.
It does not select `/output/0/content/0/text`; use
`/output/*/content/*/text` for that shape. Relay does not support `**`,
predicates, or arbitrary JSONPath expressions. `target_paths = ["/*"]`
continues to select a literal `*` object key; use `target_path_globs = ["/*"]`
when `*` should be a wildcard.

Relay validates every configured path as RFC 6901 syntax before activating the
component. The empty string selects the document root. Every other pointer must
start with `/`, and `~` escapes must use `~0` for `~` or `~1` for `/`. Invalid
pointers prevent activation instead of silently leaving the intended values
unsanitized.

</details>

### Trajectory Context Preset

<details>
<summary>What the trajectory preset removes and preserves</summary>

`trajectory_context` is a fail-closed policy for metrics-oriented trajectory
export. It discards original LLM request and response payloads and generates
minimal provider-shaped projections from sanitized normalized annotations.
Only recognized built-in codec identities, or a configured legacy codec when
no active codec is present, are eligible for projection. Runtime and opaque
codec identities emit `{}` even when their payload resembles a built-in shape.
Unknown provider fields, extensions, additional choices or candidates, headers,
provider-native values, generic event data and metadata, category-profile extras,
and unknown custom-mark payloads cannot pass through those projections. Present
opaque typed JSON values become `{}`. A valid `nemo_relay.log.severity` value is
restored for marks.

Scope metadata retains only recognized `otel.status_code` values (`OK`, `ERROR`,
`UNSET`) and, for `ERROR`, Relay's fixed `error.type` classifications or `_OTHER`.
Unrecognized error types are discarded; the `full` and `gen_ai` OpenTelemetry
projections use `_OTHER` for errors without a classification. Free-form status
descriptions, exception types, and other metadata remain discarded, so redaction
preserves success/error reporting without exporting error messages or application
exception names.

Typed LLM annotations retain message roles and content-part kinds; provider,
model, and tool names; request tuning settings; finish reasons; token and cache
usage; and normalized cost amounts, currency, and source classification.
Conversational content and application identifiers use the configured
replacement, which defaults to `[REDACTED]`. Opaque typed fields become `{}`;
approved typed numeric and boolean analytics remain available. Routing metadata,
pricing provenance, optimization contribution evidence, and unknown fields are
discarded. Relay lifecycle identifiers remain unchanged.

Provider, model, tool, and metric names are intentional free-form exceptions.
Do not place user content, secrets, or personal identifiers in these fields.
All redacted application identifiers collapse to the same marker and are not
suitable correlation keys. To retain an unknown custom mark unchanged, set
`custom_mark_payload_policy = "preserve"` explicitly and only for a trusted
producer.

</details>

### Typed Metric Marks

<details>
<summary>Typed metric sanitization and allowed dimensions</summary>

Relay recognizes marks that use its `nemo.relay.metric_measurements` schema as
typed metric envelopes. PII sanitization preserves the measurement name, kind,
value type, numeric value, and histogram boundaries so the OpenTelemetry metric
exporter can validate and export the mark.

The plugin sanitizes optional text without invalidating the envelope:

- With neither `target_paths` nor `target_path_globs`, measurement descriptions and string-valued metric
  attributes follow the configured built-in action.
- With target selectors, those fields are sanitized only when their
  payload-relative JSON Pointer matches, such as
  `/measurements/0/description` or `/measurements/0/attributes/owner`.
- With `action = "remove"`, targeting a whole string-array attribute removes
  that attribute. Targeting an individual element removes that element and
  compacts the remaining array; Relay cannot use a `null` placeholder because
  typed OpenTelemetry metric attributes must remain valid homogeneous arrays.
- Outside `trajectory_context`, numeric and boolean metric attributes remain
  analytical telemetry.

The `trajectory_context` preset replaces descriptions with its configured
replacement while retaining required measurement fields. It drops every
metric attribute except an exact string value admitted by
`metric_string_attribute_allowlist`. That preset does not accept target
selectors. Its `custom_mark_payload_policy` applies only to opaque marks in the
`custom` category; it does not control Relay typed metric envelopes.

Matching is case-sensitive and requires both the attribute name and value. A
string-array attribute is retained only when every element is allowed; one
unexpected value drops the whole attribute. Values under an unlisted key,
unexpected values under a listed key, and numeric or boolean attributes are
dropped. This allowlist does not apply to descriptions, mark metadata, category
profiles, or non-metric marks. Configure fixed constants or bounded enums only;
do not list free-form identifiers or user-provided text.

On every mark, the preset preserves the reserved `nemo_relay.log.severity`
metadata field in canonical form when it contains a supported severity. For
opaque custom marks using `redact_all_leaves`, unsupported severity values and
all other opaque fields are discarded.

Refer to the **Metric dimensions** example in [Targeting and Composition](#targeting-and-composition) for a complete configuration and payload comparison.

</details>

### CLI Editor Support

<details>
<summary>Setup and interactive editing</summary>

The CLI and primary language bindings register the component. Direct Rust
applications must call
`nemo_relay_pii_redaction::component::register_pii_redaction_component()` before
validating or initializing a `pii_redaction` component.

For file discovery, precedence, merge behavior, and gateway conflict rules,
refer to [Configure](/configure-plugins/plugin-configuration-files).

The NeMo Relay CLI plugin editor exposes `pii_redaction` directly through
`nemo-relay plugins edit`.

Use the editor when you want to:

- Toggle the component on or off
- Choose `builtin` or `local_model`
- Add and order multiple redaction profiles
- Enable or disable individual profiles
- Set the LLM `codec`
- Edit `builtin` action settings such as `action`, `target_paths`,
  `target_path_globs`, `pattern`, `detector`, `replacement`, and masking fields
- Edit `local.backend` for a runtime-provided future local-model backend

The editor preserves unknown fields when it rewrites an existing
`pii_redaction` component, so future or runtime-specific settings are not
discarded by the interactive edit flow.

If your policy needs callback code instead of editor or configuration fields,
use raw middleware.

</details>

## Worked Examples

Each tab contains a complete `plugins.toml` document and synthetic event data.
**Published payload** means the value delivered to subscribers and exporters;
real provider requests, tool arguments, and application results retain their
execution values. Tool results and result annotations are separate payloads.

### Common Actions

<Tabs>
<Tab title="Redact email">

Replace detected email addresses while preserving surrounding text.

**Configuration**

```toml
version = 1

[[components]]
kind = "pii_redaction"
enabled = true

[[components.config.profiles]]
mode = "builtin"

[components.config.profiles.builtin]
action = "redact"
detector = "email"
```

**Input event payload: tool arguments**

```json
{
  "contact": "Email alice@example.com",
  "attempt": 2
}
```

**Published payload**

```json
{
  "contact": "Email [REDACTED]",
  "attempt": 2
}
```

No selectors are needed: the detector inspects every string leaf. Numeric values remain unchanged.

</Tab>
<Tab title="Redact API keys">

Replace a synthetic API key that matches the built-in `api_key` detector.

**Configuration**

```toml
version = 1

[[components]]
kind = "pii_redaction"
enabled = true

[[components.config.profiles]]
mode = "builtin"

[components.config.profiles.builtin]
action = "redact"
detector = "api_key"
```

**Input event payload: tool arguments**

```json
{
  "api_key": "sk-example12345678",
  "contact": "alice@example.com",
  "operation": "lookup"
}
```

**Published payload**

```json
{
  "api_key": "[REDACTED]",
  "contact": "alice@example.com",
  "operation": "lookup"
}
```

No selectors are needed. This detector matches supported API-key patterns;
the email remains unchanged because this profile uses only `api_key`. Use
separate profiles to apply both email and API-key redaction.

</Tab>
<Tab title="Remove a field">

Remove an entire credentials object from the event payload.

**Configuration**

```toml
version = 1

[[components]]
kind = "pii_redaction"
enabled = true

[[components.config.profiles]]
mode = "builtin"

[components.config.profiles.builtin]
action = "remove"
target_paths = ["/credentials"]
```

**Input event payload: tool arguments**

```json
{
  "credentials": {
    "token": "token-123"
  },
  "task": "lookup"
}
```

**Published payload**

```json
{
  "task": "lookup"
}
```

`remove` deletes the selected object field, including its nested values.

</Tab>
<Tab title="Mask text">

Preserve only the last four characters of an account identifier.

**Configuration**

```toml
version = 1

[[components]]
kind = "pii_redaction"
enabled = true

[[components.config.profiles]]
mode = "builtin"

[components.config.profiles.builtin]
action = "mask"
target_paths = ["/account_id"]
```

<Tabs>
<Tab title="Nested content">

Select string leaves inside content-parts arrays.

**Configuration**

```toml
version = 1

[[components]]
kind = "pii_redaction"
enabled = true

[[components.config.profiles]]
mode = "builtin"

[components.config.profiles.builtin]
action = "redact"
detector = "email"
target_path_globs = ["/messages/*/content/*/text"]
```

**Input event payload: tool arguments**

```json
{
  "messages": [
    {
      "content": [
        {
          "type": "text",
          "text": "alice@example.com"
        },
        {
          "type": "text",
          "text": "Hello"
        }
      ]
    }
  ]
}
```

**Published payload**

```json
{
  "messages": [
    {
      "content": [
        {
          "type": "text",
          "text": "[REDACTED]"
        },
        {
          "type": "text",
          "text": "Hello"
        }
      ]
    }
  ]
}
```

This example is a JSON-native tool payload whose keys happen to be `messages`
and `content`. Each `*` matches one array index. Selecting only
`/messages/0/content` would select an array and leave the email unchanged.
Putting `*` in `target_paths` would match literal keys instead of array indices.
Refer to [Path Semantics](#path-semantics) for the matching contract.

## Verify the Policy

Valid selector syntax does not guarantee that the policy changes a payload.
Enable [runtime diagnostics](/reference/diagnostics) at startup and inspect
`pii_redaction.selector_evaluated` observations for the JSON documents the
built-in sanitizer processes. Recording is best effort and depends on diagnostic
admission and retention.

| Detail | Meaning |
| --- | --- |
| `matched_paths` | Selected nodes in the original document. |
| `eligible_string_leaves` | Selected string values in the original document. |
| `affected_values` | Values actually changed or removed by the sanitizer. |

For the **Nested content** example:

| Selector Configuration | Result |
| --- | --- |
| `target_paths = ["/messages/*/content/*/text"]` | No matching array indices: `*` is literal in exact paths. |
| `target_paths = ["/messages/0/content"]` | A container matches, but no string is selected for `redact`. |
| `target_path_globs = ["/messages/*/content/*/text"]` | Two text leaves are selected; the email leaf changes. |
| Neither selector list configured | All string leaves are eligible; the email leaf changes. |

Zero counts are informational: some traffic legitimately lacks the configured
path or a matching sensitive value. Diagnostic detail includes only bounded
counts, never the original matched content.

<details>
<summary>Selection accounting and component keys</summary>

With `action = "remove"`, a child string inside a selected container can count
as selected even though removing the container prevents the sanitizer from
visiting the child. Only the removed container counts as affected. A selected
string can also remain unchanged when its detector finds nothing.

With neither selector list configured, `matched_paths` counts all visited JSON
nodes and `eligible_string_leaves` counts the eligible string nodes. Profile
observations use component keys such as `pii_redaction.selector.profile_0`, even
with a single profile. Single-policy observations use `pii_redaction.selector`.

The `trajectory_context` preset uses its semantic sanitization path rather than
this selector diagnostic. Use the preset when the goal is broad payload removal;
refer to [Trajectory Context Preset](#trajectory-context-preset).

</details>
