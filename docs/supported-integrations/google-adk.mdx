Use NeMo Relay with [Google Agent Development Kit (ADK)](https://google.github.io/adk-docs/)
to record agent activity and apply guardrails to model and tool calls.
Add `NemoRelayPlugin` to your ADK `App` to get started.

For a guided first run, follow the [Google ADK Quick Start](/getting-started/quick-start/google-adk).
This guide covers adding Relay to your app, using the ADK command line, and
recording workflows.

## Setup

Install NeMo Relay with the Google ADK extra in your project.

<Tabs>
<Tab title="uv">
```bash
uv add "nemo-relay[google-adk]"
```
</Tab>
<Tab title="pip">
```bash
pip install "nemo-relay[google-adk]"
```
</Tab>
</Tabs>

The examples use Gemini. Set your [Gemini API key](https://aistudio.google.com/apikey)
in the shell where you run the app.

<Tabs>
<Tab title="Unix shell">
```bash
export GOOGLE_API_KEY="your-api-key"
```
</Tab>
<Tab title="Windows PowerShell">
```powershell
$env:GOOGLE_API_KEY = "your-api-key"
```
</Tab>
</Tabs>

For OpenAI models, also install `google-adk[openai]`. For Anthropic models,
also install `anthropic`. Set the credentials for your chosen provider.

Relay then records the workflow and its steps, including their inputs and outputs.


Check `logs/events.jsonl` for the `weather_pipeline`, `pick_city`, and

steps have completion or failure events, but no recorded input or duration.
Pass nodes created during a run to `wrap_node` if you need those details too.

## Verify the Integration

After running `weather.py`, check the following results:

- The app prints a final response.
- `logs/events.jsonl` contains the request, agent, and model activity.
- If the agent calls `get_weather`, the file also contains that tool call.
- Each recorded start event has a matching end event.

The [quick start](/getting-started/quick-start/google-adk#verify) includes an
example that checks its tool call and event file for you.

## Observability

Relay groups recorded activity into scopes. A scope has a start event and an
end event. The end event includes the result or error.

For the weather example, the request contains the ADK run. That run contains
the weather agent. The agent contains its model and tool calls.

Relay records the following activity:

| Activity | Recorded Details |
| --- | --- |
| ADK runs | App, session, user, input message, and final response |
| Agents | Agent name, output, and errors, including child agents |
| Model calls | Provider, model name, request, response, and available token usage and cost |
| Streaming model calls | Response chunks and the final response |
| Fallback models | A separate call for each model tried, including failed attempts |
| Tool calls | Tool name, arguments, result, and errors |
| Workflows passed to `wrap_node` | Workflow and step inputs, outputs, and errors |
| Agent handoffs and tool approvals | Events for transfers, approval requests, and approval answers |

Tool calls include tools from ADK toolsets and agents used as tools.
Relay also records code execution by executors that run outside the model provider.

Provider tools, such as Google Search and the built-in code executor, run at
the model provider. Relay records the activity that the provider reports.
These records don't include tool duration.

Cancelled runs are marked as cancelled. Some cancellation records can appear
when the task finishes, the next run starts, or the runner closes.

For export options, refer to [Observability](/configure-plugins/observability/about).

## Security and Optimization

Configured Relay guardrails and intercepts apply to model and tool calls.
Guardrails can block a call or remove sensitive data. Intercepts can change
requests and results, retry calls, or use a fallback. ADK tool approvals still
apply.

For example, you can check a weather tool's arguments before it runs. You can
also remove sensitive text before Relay exports an event.

When a guardrail blocks a call, Relay raises a `RuntimeError` with a message
that starts with `guardrail rejected`. ADK can handle the error through its
model or tool error callbacks. If no callback handles it, the run stops.

When you edit a model request, keep the tool names, count, and order unchanged.
Edits must use values that ADK and the model provider accept. Invalid edits
fail the call.

If you write a tool intercept, refer to
[Tool Execution Intercept Outcomes](/reference/tool-execution-intercept-outcomes#normalized-tool-results)
for the result format.

For configuration, refer to [Plugin Configuration](/configure-plugins/plugin-configuration-files) and
[Adaptive Configuration](/configure-plugins/adaptive/about).

## Limitations

Keep these limits in mind when choosing features for your app:

- **Live model calls:** `Runner.run_live` and `RunConfig.support_cfc` record
  runs and agents. Their model calls have no Relay model events or middleware.
- **Response caching:** Relay's response cache skips ADK model calls.
- **PII redaction:** While redaction is active, Relay leaves the model
  response out of exported model end events.
- **Streaming:** Chunk events contain a brief summary. Custom models that rely
  on when chunks are requested or when a stream closes can behave differently.
- **Parallel workflow workers:** Steps run with ADK's `parallel_worker` option
  have completion events rather than full step scopes.
- **Provider tools:** Relay cannot block or change tools that run at the model
  provider. It can sanitize their recorded events. To record `url_context`,
  enable `include_server_side_tool_invocations` in your Gemini request.
- **Custom extensions:** Code that relies on exact model, tool, or agent
  classes, or changes class attributes during a run, can behave differently.

Only model classes supported by the integration can use all of these features.
An unsupported built-in ADK model class fails the call. A custom `BaseLlm`
can use Relay, but provider details depend on the response data it supplies.
