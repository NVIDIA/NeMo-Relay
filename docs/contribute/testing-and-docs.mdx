This page describes the validation and documentation checks expected for repository
changes.

## Testing Rule

Run tests for every language surface whose observable behavior can change. Start
with the smallest focused test that proves the change, then run the canonical
suite for each directly affected surface before handoff. A Rust implementation
change does not automatically require every binding suite. Add a binding suite
when the shared change affects that binding's public or observable contract.

Run the affected targets directly:

```bash
just test-rust

# Run Rust tests with code coverage reporting, requires installing cargo-llvm-cov with `cargo install cargo-llvm-cov`
just ci=true test-rust

just test-python
just test-go
just test-node
just test-openclaw
```

The Rust-backed test recipes use `cargo-nextest`; install it with
`cargo install cargo-nextest --version 0.9.133 --locked` before running them.

The Rust, Python, and Go recipes build the native and worker dynamic-plugin test
fixtures once before starting their test runners. Before a focused raw test that
uses those fixtures, prepare them explicitly:

```bash
just build-test-plugin-fixtures
```

Keep normal hermetic test cases below five seconds. Do not compile packages or
fixtures inside a test case, keep real-time synchronization guards at five
seconds or less, and use virtual time when validating timer behavior. Package
builds and opt-in live end-to-end checks remain separate validation steps with
their own runtime budgets.

Run integration, documentation, packaging, FFI, generated-output, or build-only
checks only when those surfaces change or the relevant test does not build
them. Documentation, comments, mechanical metadata, and other reversible
low-impact changes do not require language suites or tests that merely mirror
the implementation. CI remains the broader cross-platform backstop.

Use the matching build recipes when you need explicit build-only passes:

```bash
just build-rust
just build-python
just build-go
just build-node
```

## Common Commands

These commands cover the most common language-specific validation loops.

### Rust

Run the Rust validation loop when a change touches the core runtime or
Rust-facing API surface.

```bash
just test-rust
```

### Python

Run the Python validation loop when a change touches the wrapper package, tests,
or docs tooling.

```bash
uv sync
just build-test-plugin-fixtures
uv run pytest
```

### Node.js

Run the Node.js validation loop when a change touches the NAPI binding or
JavaScript package surface. Run the OpenClaw target when Node changes can affect
the OpenClaw plugin or when touching `integrations/openclaw`.

```bash
npm install --ignore-scripts
npm test --workspace=nemo-relay-node
just test-openclaw
```

## Documentation Checklist

If your change affects public behavior, bindings, examples, or workspace structure, update the corresponding docs in the same branch.

Before opening a PR, confirm:

1. `README.md` still matches the repo structure
2. Relevant reference docs are updated for public API changes.
3. Relevant package or crate READMEs are updated when needed.
4. Examples and snippets stay aligned with supported bindings.
5. Docs build cleanly.

## Docs Verification

Use `just docs` to validate the Fern documentation site after relevant docs
changes. It regenerates the ignored Python, Node.js, and Rust API reference
pages before checking links and navigation. `just docs-linkcheck` is the
compatibility entry point for a link-focused run; the recipes currently perform
the same validation, so do not run both.

```bash
just docs
```

### Quickstart Contracts

Quickstart pages own their executable examples and success criteria. Hidden
`quickstart-scenario` and `quickstart-block` JSON comments label the existing
MDX fences; do not maintain a second copy of their commands in CI.
`just docs` checks these contracts without installing packages or calling a model.

From the repository root:

```bash
python3 scripts/check-quickstarts.py check
python3 -m unittest discover -s scripts/tests -p test_quickstarts.py
python3 scripts/check-quickstarts.py extract docs/getting-started/quick-start/python.mdx --shell bash
```

The extractor requires Python 3.11 or newer and has no third-party dependencies.
Each page declares its prerequisites, live-provider requirements, fresh output
paths, and artifact checks. Each fence has a stable ID and one role:

- `file`: write the fence verbatim to its `path`, relative to the block's `cwd`.
- `run`: execute in the declared shell, directory, and session, with the stated
  timeout. Require exit code zero before continuing. Retain session environment
  variables, but set the declared working directory before each block.
- `input`: show the reader how to set a credential. Automation supplies the
  declared environment variable from its secret store; never execute the
  placeholder assignment or put the secret into the extracted JSON.
- `manual`: an interactive prerequisite, such as Hermes onboarding. An unattended
  test must provision it explicitly and record the installed host version.
- `expected`: exact stdout lines from the command named by `from`. Capture
  stderr separately. Newline conventions may differ; extra output does not pass.

For file and command placeholders, the page declares the literal token and
whether its replacement is a path or argument. A future executor must encode
replacements for the target file format or shell, not concatenate untrusted
values into a command. The current extractor preserves these tokens.

To verify a run, use a fresh disposable workspace and run `preflight` **before**
executing the extracted recipe. For example, if `/tmp/relay-test` is your workspace
and `/tmp/python.stdout` contains stdout from its successful `run` block:

```bash
python3 scripts/check-quickstarts.py preflight docs/getting-started/quick-start/python.mdx --workspace /tmp/relay-test
python3 scripts/check-quickstarts.py verify docs/getting-started/quick-start/python.mdx --workspace /tmp/relay-test --stdout /tmp/python.stdout
```

These commands inspect freshness and results; they do **not** execute the recipe.
The workspace is the parent of the documented project directory. OpenClaw also
needs explicit `--input RELAY_LOG_DIR=<absolute-directory>` and
`--input AGENT_WORKSPACE=<absolute-directory>` values for artifact checks.

The verifier parses every JSONL record and requires the page's named lifecycle
pairs or marks, plus its tool artifact or structured model response where
applicable. UUIDs and timestamps are validated as fields, not compared to a
snapshot. Prompt echoes and marker strings buried in unrelated JSON do not count.
Use fresh output paths and an isolated host profile to prevent stale or unrelated
traffic from satisfying a check; no post-run verifier can prove freshness alone.

Python, Node.js, Rust, and LangGraph are credential-free local scenarios.
The other pages are live scenarios: deterministic assertions do not make their
providers deterministic. No mock-provider substitution is currently declared.
Hermes authentication and OpenClaw agent/gateway provisioning remain explicit
setup requirements, not hidden test adapters.

For Switchyard, the process annotation specifies readiness, the shutdown
boundary before verification, and a bounded interrupt/cleanup timeout. A runner
must reject an occupied port, ensure its own process stays alive, interrupt it
after the request, and force-stop only that owned process if cleanup times out.
PowerShell runners must also fail on nonzero native-process exit codes; setting
`$ErrorActionPreference` alone does not provide that guarantee in every version.

The full cross-platform executor and CI support matrix are a separate step.
Select only shell variants and host/package combinations supported by the
published release; the presence of a PowerShell recipe is not a platform test
result. Never run these install and gateway commands against a maintainer's
normal profile as part of an untrusted pull-request job.

## Fern Publishing

NeMo Relay uses a dual-branch Fern publishing model. Authors edit documentation
on `main` in `docs/` and `fern/`. The generated Fern content on
`docs-website` is managed by CI and must not be edited by hand. The branch root
`.gitignore`, `README.md`, and `.github/workflows/publish-fern-docs.yml` are
branch-local maintenance files and can be updated directly on `docs-website`.

The Fern workflow uses the `FERN_TOKEN` GitHub environment secret from the
`fern` environment. Pull-request branches under `pull-request/**` get Fern
previews when docs change, and merged pull requests clean up their preview
deployment. Pushes to `main` sync the generated `fern/pages-dev/` layout to
`docs-website` and publish the dev docs. Raw SemVer tags such as `0.1.0`,
`0.1.0-beta.1`, and `0.1.0-rc.1` create public docs versions displayed with a
leading `v`. Prerelease indicators are stripped from the public docs version
path, so `0.1.0-beta.1`, `0.1.0-rc.1`, and `0.1.0` all target `v0.1.0`. Stable
tags use `availability: stable` and update the default `Latest` version. Beta
and release-candidate tags use `availability: beta`, replace the same base
version snapshot, and do not update `Latest`. Alpha tags are not published.

The branch sync and version snapshot logic lives in
`scripts/docs/sync_fern_docs_branch.py`.
