**Middleware adds rules and behavior around tool and LLM calls without changing
the code that performs the underlying work.** Relay uses it to check or modify
requests, allow or block execution, add retries or fallbacks, and control what
data is recorded in events.

## What You Build

You will add middleware to a working Execute call and verify its effect:

- Request intercepts transform the real request before execution.
- Sanitize guardrails transform only the payload recorded on events.
- Conditional-execution guardrails can block execution.
- Execution intercepts wrap the callback and can add timing, retries, routing, or fallback behavior.
- Application execution context supplies invocation-local information to execution
  intercepts, such as an existing approval assertion.

## Before You Start

Complete [Instrument a Tool Call](/instrument-applications/instrument-tool-call)
or [Instrument an LLM Call](/instrument-applications/instrument-llm-call).
Execute APIs run execution-control middleware around the actual callback. Manual
start/end APIs apply event-payload sanitizers but do not automatically run request
or execution intercepts.

## Choose the Middleware Type

Use this table to match the behavior you need with the correct middleware family.

| Need | Middleware Type | Changes Real Execution |
|---|---|---|
| Redact event payloads | Sanitize-request or sanitize-response guardrail | No |
| Normalize tool arguments or model requests | Request intercept | Yes |
| Block unsafe or invalid work | Conditional-execution guardrail | Yes, by rejecting |
| Add timing, retries, routing, or fallback | Execution intercept | Yes |
| Wrap streaming model output | LLM stream execution intercept | Yes |

Use the narrowest middleware type that matches the behavior. For example, do not use a request intercept when you only need to hide a secret from exported events.

## Application Execution Context

An application can adopt execution middleware incrementally while retaining its
existing human approval flow. For example, it can supply a reference to a
completed application review separately from the tool's business arguments. A
middleware component that understands that review can avoid repeating its own
review, then call `next` so the remaining middleware and tool callback still run.
Relay does not interpret the reference or change the approval flow itself.

The application APIs carry the same optional value through each binding. Supply
it on the managed execute call, then read it from the middleware context:

| Binding | Supply context when executing | Read it in execution middleware |
| --- | --- | --- |
| Rust | `ToolCallExecuteParams::builder().execution_context(value)` | `context.execution_context()` |
| Python | `tools.execute(..., execution_context=value)` | `context.execution_context` |
| Node.js | `executionContext` in `typedToolExecute` options | `context.executionContext` |
| Go | `WithApplicationExecutionContext(value)` on `ToolCallExecute` or `tools.Execute` | `context.ExecutionContext` (`*ApplicationExecutionContext`) |
| C | `execution_context_json` on `nemo_relay_tool_call_execute_with_context` | Optional `execution_context` property in the callback's context JSON |

Rust and Python worker SDKs expose the same optional context on their tool
execution callback. The C entry point is additive: existing execute functions
retain their signatures and omit context. Go rejects the option on manual
`ToolCall` and `ToolCallEnd`, where execution middleware does not run.

The value follows the standard `ApplicationExecutionContext` JSON Schema. Its
optional `host_approval` field asserts that the application has already verified
human approval for an exact operation:

```json
{
  "host_approval": {
    "version": 1,
    "source": "example.application",
    "approval_id": "approval-123",
    "tool_name": "files.write",
    "approved_arguments": {"path": "notes.txt", "content": "Hello"}
  },
  "com.example.audit": {"request_id": "request-456"}
}
```

When `host_approval` is present, it asserts completed affirmative human approval
and all five fields are required. Version is integer `1`; source, approval ID and tool name
are nonempty strings. Approved arguments may be any JSON value, matching tool
arguments. They record the approved input so middleware can compare it with its
current input after earlier middleware has rewritten arguments. Denied or
pending operations must stop in the application; this field is not an instruction
to Relay to enforce a review outcome.

Both the context and the approval object allow additional properties. The obsolete
`host_approval.decision` key is reserved and rejected regardless of value, so an
old denied claim cannot become an ignored extension interpreted as approval. Unknown
properties survive transport and isolated snapshots, but confer no authority.
Use namespaced extension keys, such as `com.example.audit`, to reduce collisions
with future standard fields. Omission means no context; `{}` is a supplied empty
context with no approval assertion. An explicitly null or malformed
`host_approval` is rejected rather than treated as absent.

The entire context, including extensions, must serialize to at most **16 KiB**
of UTF-8 JSON and contain at most **64 nested container levels**. The root object
counts as level 1; nested objects and arrays add one level each. Limits are checked
before JSON Schema traversal. Invalid known fields fail before middleware or the
tool runs. Structural validation does not authenticate an approval.

The canonical schema is maintained with the shared Rust types in
[`application-execution-context.schema.json`](../../crates/types/schemas/application-execution-context.schema.json).
Rust exposes `ApplicationExecutionContext` and `HostApproval`; other bindings and
worker SDKs expose the same fields using their native typing conventions.

Rust callers can construct the checked type with
`ApplicationExecutionContext::try_from(json_value)?` before passing it to the
managed execution builder. Admission also revalidates values assembled or
modified through public Rust fields. Python keeps dictionary-compatible typed
shapes; additional properties remain accepted at runtime despite Python 3.11's
`TypedDict` limitations. Go offers `WithApplicationExecutionContext` for its typed
model and retains `WithToolExecutionContext` for schema-validated raw JSON.

This field has a narrower lifetime and audience than event metadata:

- Only execution intercepts receive it. Tool arguments, request intercepts,
  conditional guardrails, and the final tool callback do not receive it as a
  separate parameter.
- Each intercept receives an isolated snapshot. Changes to a binding-local
  object do not change what another intercept sees. Calling `next` can rewrite
  business arguments, but cannot replace the execution context.
- A nested managed tool call has no execution context unless its caller supplies
  one explicitly. Scope metadata does not populate it automatically.
- Relay does not automatically copy it to lifecycle events, results,
  annotations, or telemetry. Application and plugin code can still disclose it
  explicitly, so avoid logging it or adding credentials to it.

Application-supplied does **not** mean verified authorization. Relay does not
verify a human decision, caller identity, signature, expiry, or operation binding
inside this object. The application must validate its own approval proof and
bind it to the exact tool, business arguments, owner and applicable policy before
supplying a review claim. Do not populate it from a model-generated `approved`
flag. An intercept must also check that the claim still covers its current
arguments, because earlier middleware may have rewritten them. Missing,
unrecognized or mismatched claims should use that component's normal review
path; they must not imply approval. The application must stop a human-denied
operation rather than ask middleware to override that denial. If human approval
is mandatory and the operation changes, the application must reject it or obtain
fresh approval; a component's automated review does not renew human consent.

The following tested integration sketch accepts application-defined
`validate_existing_approval`, `approval_covers_call` and
`perform_component_review` functions as callbacks; Relay does not implement them.
The verifier and trust matcher are synchronous; the component reviewer is
asynchronous. Call `register_application_review(...)` once during setup, then use
`execute_after_application_approval(...)` to execute an approved operation.
The verifier must raise if the receipt is invalid or no longer covers the call.
`perform_component_review` must raise to refuse execution; returning `False`

five-field
`host_approval` assertion only after verifying the application-specific receipt;

### Transport Compatibility

**Application package requirements**

Use compliant Relay 1.0 components built from the matching package set. For
Node.js this includes both the JavaScript/TypeScript wrapper and its compiled
native binding; do not mix them with earlier development snapshots. Execution
context is part of the required API contract, not an optionally detected feature.
Use `executionContext` directly in the managed execute options.

The same matching-version requirement applies to Rust, Python, Go and C. Rebuild
bindings and workers together when the unreleased 1.0 baseline changes. This
requirement does not replace input validation: context must still be an object
within the size and nesting limits, and supplying it grants no authorization.

**Worker-side compatibility checks**

Execution-context support is required by
`nvidia.nemo.relay.worker.v1@1.0.0`, not an optional SDK capability. Hosts and
workers check protocol identity and exact contract version before registration.
Every conforming worker must preserve supplied context, including `{}`. The
application can still omit context on any call, and callback signatures remain
unchanged. The handshake establishes the declared protocol contract, not
permission to execute or proof of application approval.

Relay 1.0 has not yet been released. Rebuild and repackage development workers
with the matching SDK rather than relying on compatibility with an earlier
development snapshot. An obsolete binary that advertises the same `1.0.0`
identity cannot be detected by version alone; the contract requires it to be
rebuilt. Separately versioned diagnostic contracts are unchanged.

**Native plugin compatibility**

The current SDK's typed native tool registration uses native contract **v1.1**
and exposes checked context through `context.execution_context()`. This native
contract version is separate from Relay's package version **1.0**.
The host checks the required native contract before creating the plugin.
Published native v1.0 plugins still load and handle calls without application
context as before. If supplied context reaches a legacy v1.0 tool callback,
Relay refuses the call explicitly instead of dropping the context. This also
applies to explicit legacy registrations in a newly built v1.1 library. Use
the SDK's typed tool registration or the v1.1 tool interface to receive context;
rebuilding alone does not migrate a legacy registration.
See [Native ABI Reference](/build-plugins/native/native-abi-reference#application-execution-context)
for the additive transport. Public C and Go callbacks receive context through
their extensible JSON envelope.

## Scope Middleware to One Request

Use scope-local middleware when a policy applies only to one request, tenant, experiment, or agent run.

1. Create or receive the active scope handle.
2. Register middleware with the scope-local helper for that handle.
3. Execute tools or LLM calls inside that scope.
4. Let the scope end remove the scope-local registrations automatically.

Use global middleware for process-wide behavior, such as organization-wide redaction. Use scope-local middleware for request-specific policy, such as tenant routing or an A/B test.

## Configure Execution Stages per Call

Each managed tool or LLM call can choose which middleware stages run. You can
turn conditional-execution guardrails, request intercepts, and execution
intercepts on or off. All three stages run by default and keep their usual
order. If you turn off conditional execution, Relay skips those checks for that
call. Only skip checks when your application no longer needs them for that call.

For example, your framework might apply request intercepts before it calls
Relay. Turn off that stage to avoid running it twice. Keep the other stages on.
Use the call from your working tool or LLM example and change only its options.

Options affect only the call that receives them. Nested calls and calls that
run at the same time use their own options. These controls select whole stages,
including global and scope-local registrations. They do not change stage order
or select individual registrations by name. Use
[Control a Global Registration](#control-a-global-registration) to control a
specific global registration instead.

Relay still sanitizes event data, uses codecs, passes trace context, and handles
call completion. With all three stages off, Relay still emits start and end
events and cleans up streams. For streaming LLM calls, `execution_intercepts`
controls the streaming execution intercepts. The collector, finalizer, and stream
close behavior stay active.

Turning off request intercepts does not turn off codec processing or session
headers. The provider request can therefore differ from the input request.
These options do not change manual start/end APIs or standalone middleware helpers.

## Control a Global Registration

Use a conditional middleware guardrail when an operational policy must temporarily
exclude existing global middleware or a subscriber. Discover the target from the active
runtime, and match its registration kind and effective name. Do not persist or construct
the effective name.

The gate affects future middleware and event-publication snapshots. It does not change
an in-flight chain, a queued event, the target's ownership, or a same-named scope-local
registration. Every matching gate must allow the target. If a gate callback fails, Relay
fails open and keeps the target eligible.

Choose one of the following lifecycle patterns:

- Register a global gate when application code owns the timer, health check, or
  operational control. Remove the gate in a guaranteed cleanup path.
- Register an activation-owned gate when a plugin component owns the control for its
  complete active lifetime. Relay removes the gate during rollback or teardown.

Gate callbacks must read already-available state. They must not make reentrant Relay
calls that produce middleware, flush subscribers, wait for exporters, or clear plugins.
Refer to
[Conditional Middleware Guardrails](/about-nemo-relay/concepts/conditional-middleware-guardrails)
for the complete semantic model and [Code Examples](/instrument-applications/code-examples)
for binding-specific registration and cleanup.

## Middleware Registration Families

NeMo Relay exposes the same core middleware families for tools and LLMs:

| Family | Tool Registration | LLM Registration | Changes Real Execution |
|---|---|---|---|
| Sanitize request | `register_tool_sanitize_request` | `register_llm_sanitize_request` | No |
| Sanitize response | `register_tool_sanitize_response` | `register_llm_sanitize_response` | No |
| Conditional execution | `register_tool_conditional_execution` | `register_llm_conditional_execution` | Yes, by rejecting |
| Request intercept | `register_tool_request` | `register_llm_request` | Yes |
| Execution intercept | `register_tool_execution` | `register_llm_execution` | Yes |
| Stream execution intercept | Not applicable | `register_llm_stream_execution` | Yes |

Sanitize guardrails affect only the payload recorded on emitted events. Tool
sanitize-response guardrails receive only `ToolExecutionResult.result`; a
scope-end event sanitizer can separately sanitize the projected tool result
annotation. Request intercepts affect the real request that reaches the tool or
provider. Execution intercepts wrap the callback itself and are only available
when the invocation uses managed execution.

A tool execution intercept receives a `ToolExecutionContext` carrying the tool
name, the arguments, and the managed `tool_call_id`. Use it when an intercept
short-circuits execution and must still correlate its result with the
originating tool call. See
[Tool Execution Intercept Outcomes](/reference/tool-execution-intercept-outcomes)
for the per-binding contract.

### Node.js Callback Failures

Node.js guardrail and request-intercept callbacks can return direct values or
Promises. A thrown error or rejected Promise from a conditional-execution
guardrail or request intercept rejects the managed call before protected
execution or later middleware runs. A thrown error or rejected Promise from a
sanitize guardrail or event sanitizer fails closed, withholding the governed
emitted payload and recording the error for `getLastCallbackError()`.

Scope-local variants are available through `nemo_relay.scope_local.register_*`, Node.js `scopeRegister*` helpers, and Rust `scope_register_*` functions.

## Debug Middleware Order

Middleware runs by ascending priority inside each middleware family. Families
and lifecycle emission run in this order for managed tool calls:

1. Conditional-execution guardrails.
2. Request intercepts.
3. Sanitize-request guardrails and start-event emission.
4. Execution intercepts and the real callback or replacement.
5. Sanitize-response guardrails and end-event emission.

If a later middleware does not run, check whether an earlier conditional-execution guardrail rejected the call or a request intercept raised an error.

## Common Issues

Check these symptoms first when the workflow does not behave as expected.

### Sanitized Data Reaches the Real Tool

Use a sanitize guardrail only for event payloads. Use a request intercept when the real request should change.

### Middleware Affects Unrelated Requests

Register it scope-locally instead of globally.

<Anchor id="duplicate-names-replace-behavior">

### A Middleware Name Is Already Registered

Registering middleware under a name already in use fails. Choose a unique
name, or explicitly deregister the existing middleware before registering its
replacement.

</Anchor>

### Execution Intercept Never Prints

Confirm that the application uses the managed execute helper and that no guardrail rejected the request.
